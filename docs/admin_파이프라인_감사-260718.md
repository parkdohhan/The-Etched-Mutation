# admin 파이프라인 감사 — 작가 통제 → 데이터 적재 전 구간 (2026-07-18)

> 질문: 작가가 admin만으로 **완전히 재생 가능한 기억을 통제**할 수 있는가, 그리고 그게
> **스키마 명세대로 데이터로 쌓이는가.**
> 방법: 지휘 세션이 playwright로 시험 기억 1개를 admin에서 처음부터 저작 → 시딩 → 재생 →
> 봉인까지 완주, 각 단계를 브라우저 내 Supabase 클라이언트로 실측(실전 경로). Supabase MCP
> 부재로 service-role 대신 익명/인증 세션 사용 — 오히려 관객 실경로와 동일.
> 대상: 시험 기억 `AUDIT-PIPE-01` (memory_id `db8aa4ba-4de4-4939-8e3a-9e7b14875302`).

## 판정 — 파이프라인 전 구간 통과 (잔여 정리 1건)

작가가 admin만으로 완전한 재생 가능 기억을 만들 수 있고, 재생 데이터가 명세 §5대로
인구 분리되어 쌓인다. **오전(7-17) UX검수에서 "admin으로 못 넣던 4개 구멍"이 W3로 전량
봉합됨을 실증.**

## 커버리지 매트릭스 (저작 가능 → DB 안착 → 재생/데이터 반영)

## 인구 분리 실측 (명세 §5 핵심 안전장치)

- **시딩 전후 실관객 수: 12 → 12 (불변).** author-seed가 실관객 쿼리
  (`persona_id IS NULL`)에 안 섞임.
- 이 기억의 plays 3인구: 실관객 1(내 플레이) / 작가시딩 2 / wave레거시 1 — 서로 격리.
- 논문 분석 쿼리(§5 부록)가 실관객 1행만 정확히 집어냄.

## 저작→재생 소비 사슬 (실증 하이라이트)

내가 admin `dialog_choices` 편집기에 입력한 유령 도입부 2번째 줄
("네 발자국이 낯익어")이 **play-test 재생에서 그대로 출력됨.** 즉 작가 손 콘텐츠가
런타임 소비자(lumen_dialog_phase1)에 정확히 도달. 저작-소비 스키마 일치 확정.

## 발견·잔여

1. **[R3-N1 재확인 — plays DELETE 정책 부재]** 시험 정리 시 memory·scenes·terrain·
   admin_versions는 인증 세션으로 삭제됐으나 **plays 4행은 삭제 침묵 차단**(200-0행,
   에러 없음). service-role(Supabase MCP)로만 삭제 가능. 이는 신규 결함이 아니라
   기지 이슈(R3-N1)의 재확인.
   - ⚠️ **잔여 정리 필요**: Supabase MCP 복귀 시
     `DELETE FROM plays WHERE memory_id='db8aa4ba-4de4-4939-8e3a-9e7b14875302'` (4행).
   - ✅ **무해 확인**: 씬 삭제로 4행의 scene_id가 전부 SET NULL → 명세 §5의
     `scene_id IS NOT NULL` 필터에 전량 탈락(pollutes_real_audience=0). 실관객 분석·
     지형·오염에 오염 0. §5 규칙이 이 고아 케이스를 자동 방어함이 실증됨.
2. **[§6-7 재확인]** admin 저장 1회당 wave 레거시 행(scene_id null) 1개 삽입. §5 유효행
   필터로 배제. 4차 위생 후보 유지.
3. **[저작 미완 주의]** 씬1에 감정 미입력 시 시딩이 빈 감정으로 심음(버그 아님).
   작가는 모든 씬에 감정(choices 또는 Canvas 17축) 입력 필요 — 시딩 전 체크리스트 항목.

## 결론

**작가 통제·데이터 적재 파이프라인은 알파 가동 준비 완료.** 남은 건 잔여 plays 4행의
service-role 정리 1건(무해)뿐. admin이 재생 가능한 완전 기억의 단일 저작 창구로 기능함을
전 구간 실증했다.
