**팩트: index.html과 play-test.html은 부모가 다른 형제임.**
- `index.html` → `js/index.js`를 ES모듈로 부름 → 거기서 80개 파일이 `import`로 줄줄이 딸려옴.
- `play-test.html` → `lumen_*` 파일들을 옛날식 `<script>` 태그로 부름 → 얘들끼린 `import` 안 쓰고 `window.전역변수`로 손잡음.

모듈 시스템부터 다름. **한 레포 안에 다른 시대에 지어진 건물 두 채가 있는 거임.**

## 2. 🔥 촌철살인 — tem은 작품이 두 개다

이게 이 글의 핵심임. 정렬도(=체험자가 원본 기억과 얼마나 닮게 느꼈나, 작품의 심장) 계산을:

- **`index.html` 쪽**은 `js/core/ByeoriEngine.js`(별이엔진 V4)가 함. `alignment = level × shape × void_mod` 공식.
- **`play-test.html` 쪽**은 `js/ui/lumen_dialog_phase1.js`가 *자체 `_cosineSim` 함수*로 함. 별이엔진 안 부름. 아예 import도 안 함.

ㄹㅇ로 grep해봄. 별이엔진을 부르는 파일 목록에 `lumen_*`은 한 개도 없음. LUMEN은 drift픽·ghost_variants라는 *딴 시스템*으로 굴러감.

> **그래서 "어디를 고쳐야 현재성이 올라가냐"는 질문이 핀트가 안 잡힘.** 고칠 엔진이 두 개고, 7월 데모가 어느 쪽인지 코드에 안 적혀 있으니까. 작가가 시스템을 체화 못 한 게 아니라, 시스템이 체화 가능한 한 덩어리가 아닌 거임. 이거부터 정해야 함 — **둘 중 뭐가 진짜 TEM이냐, 아니면 합칠 거냐.**

## 4. 🎯 index.html 세계 — 파일 전수조사 (중요한 순)

### 🔴 S티어 — 심장. 이거 멈추면 작품이 송장 됨

- **`js/core/ByeoriEngine.js`** (181줄) — 별이엔진 V4. 작품의 심장. "체험자가 원본 기억과 얼마나 닮게 느꼈나"를 `alignment = level × shape × void_mod`로 계산. level=장면별 감정 유사도 평균, shape=감정 변화 궤적 닮음, void_mod=침묵하면 ×0.7. **판단 안 하고 숫자만 뱉음.** 181줄밖에 안 되는데 작품 전체가 여기 매달림.
- **`js/core/ContaminationTracker.js`** (470줄) — 오염 추적기. 별이엔진 출력을 받아서 기억이 얼마나 변질됐는지(divergence/convergence/heterogeneity 3축 + drift/fixation 2축) 계산. **세션 끝날 때 1번만 돌아감.** 별이엔진은 절대 안 건드리고 출력만 소비함.
- **`js/core/SceneNavigator.js`** (190줄) — 다음 장면 고르는 놈. "패턴이 반지름이 아니라 기하(중심)를 바꾼다"는 규칙. echo_follow면 원본 쪽, contradiction이면 반대쪽으로 탐색 중심을 옮김.
- **`js/shared/math.js`** (562줄) — 모든 계산의 바닥. 코사인 유사도, VAD 투영, shape/level 계산 다 여기. 별이엔진도 얘 없으면 못 삼.
- **`js/shared/tem_geo_map.js`** (43줄) — "World Constant. 값 절대 변경하지 않는다"고 헤더에 박혀있음. 17감정의 VAD 좌표(공포는 어디, 슬픔은 어디). 43줄짜리 헌법임.
- **`js/app/appStore.js`** (62줄) + **`js/core/store.js`** (72줄) — 전역 상태함. 지금 무슨 모드, 몇 번째 장면, 정렬도 얼마인지 여기 다 들어있음. store.js가 엔진(createStore), appStore.js가 그 인스턴스.

### 🟠 A티어 — 플레이 본체. 화면에서 실제로 굴러가는 것

- **`js/index.js`** (882줄) — index.html의 지휘자. 20개 모듈 import하고 메뉴 라우팅(PLAY/ARCHIVE/RECORD). `window.byeoriEngine = byeoriEngine` 박는 것도 얘 — 그래서 expInterview가 엔진을 쓸 수 있음.
- **`js/app/archive.js`** (2145줄) — **텍스트 아카이브 플레이 본체.** 헤더 왈: "memory list, 장면 렌더, 감정 입력, 엔진 통합, 플레이 추적, 파동". 장면 보여주고 → 입력 받고 → 엔진 돌리고 → 다음 장면. 큰 만큼 잡일 다 함.

## 8. 데이터가 흐르는 길 (play 한 판이 어떻게 도나)

**index.html(텍스트) 한 판:**
```
오프닝(opening.js) → 멀티턴 매칭 → 기억 선택 → archive.js가 장면 렌더
  → 플레이어 감정 입력 → expInterview.js가 칩으로 수집
  → window.byeoriEngine.calculateStep() = 정렬도 계산
  → applyEngineResult로 상태 저장 → SceneNavigator가 다음 장면 결정
  → (반복) → 세션 끝 → ContaminationTracker가 오염 1회 갱신 → endScreen
```

**play-test.html(LUMEN) 한 판:**
```
?memory=아이디로 직진입 → tem_af_strata_terrain이 3D 지형 생성
  → 1인칭 보행(walk_effects) → 유령 만남(scene_ghosts/mannequins)
  → lumen_dialog_phase1이 대화 진행 + 자체 alignment 계산
  → drift픽(DriftPicker) → void 빠지면 rewind 되감기
  → lumen_run_outro 한 줄 엔딩 → record-drift-cumulative로 누적 갱신
```

**두 길이 만나는 지점이 거의 없음.** 이게 핵심임.

## 9. 갤러 결론 + 작가한테 하는 말

- tem 코드는 잘 짜인 편임. 파일마다 헤더에 자기가 뭐 하는지 적어놨고, "이 함수 건드리지 마", "이건 wrap만 해" 같은 규율이 곳곳에 박혀 있음. 코드 자체는 양호함.
- **문제는 코드가 아니라 "어느 게 본진이냐"가 안 정해진 거임.** index.html(텍스트)과 play-test.html(LUMEN), 둘 다 살아있고 둘 다 최근 커밋이 있음. 정렬 엔진도 따로 굴러감.
- 그래서 작가가 "내 시스템을 체화 못 했다"고 느끼는 건 당연함 — **체화할 대상이 하나가 아니니까.** 두 작품 중 7월 데모 본진을 정하는 게 1번임. 그거 정하면 나머지 분석이 다 핀트 잡힘.

> 다음에 "어디를 고쳐야 하나" 같은 질문 나오면 — **먼저 "index냐 play-test냐"부터 답하고 시작해라.** 안 그러면 또 엉뚱한 파일 깐다.
