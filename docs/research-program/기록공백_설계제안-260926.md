# 기록 공백 설계 제안 — 10월 손잡이 튜닝 전에 정할 것 (2026-09-26)

> 목적: [TEM_research_spec_v0.1-260926.md](TEM_research_spec_v0.1-260926.md) 원문 §4 "엔진을 변형한 경우 그 개입을 기록한다"와 §6 "최소 기록 명세"를 현행 스키마에 맞춰 **최소 침습**으로 채우는 안. 10월 지형 손잡이 튜닝(이본지층 설계 §3 "10월 튜닝 대상")이 시작되면 "이 행은 어느 값으로 구워졌나"를 사후 복원할 수 없게 되므로, 튜닝 **전에** 자리를 정해야 한다.
> 상태: 제안. 코드·마이그레이션 변경 0. 실행은 사용자 승인 뒤 별도 세션.

## 0. 결론 한 줄

**`run_journals`에 `provenance jsonb` 열 하나를 추가하고, 회차 시작 시 실제 메모리 값(손잡이·상수·플래그·프롬프트 버전·캐시버스터)을 스냅샷으로 한 번 쓴다.** 실험 조건·사슬 열도 같은 표에 둔다(안 B). 예측값 표는 지금 만들지 않는다(§4).

## 3. 제안

### 안 A (권장) — `run_journals.provenance jsonb` 1열, 회차 시작 시 1회 patch

왜 `run_journals`인가:
- 이미 **회차당 1행**이고 사건마다 patch하는 구조. plays는 씬마다 1행이라 같은 값이 N번 중복된다.
- play-test 주석(4733) "plays 행 수를 세는 지표(오염도 평균·깊이·겹)에 안 섞인다"는 원칙과 정합.
- plays·terrain_layers·trajectory_bridges 전부 `run_id`로 조인된다 → 한 곳에만 쓰면 된다.
- RLS: run_journals는 이미 anon insert/update가 열려 있다(현행 patch가 동작 중).

무엇을 쓰나 — **손으로 관리하는 버전 문자열이 아니라 그 순간 메모리에 있는 실제 값**:

```
provenance: {
  written_at, client_build: '<play-test 캐시버스터 최댓값>',
  engine: {
    byeori: 'v4', contamination: 'mvp_v3+v2_3axis', strata: 'w1-6',
    access: 'pattern-center-260727', cut: null   // 플레이 경로엔 절단 없음
  },
  prompts: { dialog_turn: '<dialog-turn 응답의 prompt_version>' },
  handles: {
    strata: TemVariantStrata.HANDLES,            // 6개 그대로
    contamination: { EMA_ALPHA, DRIFT_WEIGHTS, FIX_WEIGHTS, STAGE_THRESHOLDS, DECAY_RATE, ... },
    access: PATTERN_CENTER + 반경 상수,
    stage_text: { DEPTH_STAGE_2, DEPTH_STAGE_3 },
    resonance: { contact: 0.85, vague: 0.5 }
  },
  flags: { variant_strata: TemVariantStrata.isEnabled() },
  condition_id: null, chain_id: null, parent_run_id: null   // 안 B
}
```

크기 ≈ 1~2KB. 손잡이를 바꾸는 커밋이 값을 바꾸면 **자동으로** 다음 회차부터 다른 스냅샷이 남는다 — 사람이 버전 문자열 올리는 걸 잊어도 값은 맞다(7-17 캐시버스터 미갱신 사고의 반복 방지).

비용: 마이그레이션 1열 + play-test에 patch 호출 1자리(회차 시작, `game._runId` 생성 직후) + 상수 3묶음을 한 객체로 모으는 함수 1개. 롤백 = 열 방치(무해).

하지 않는 것: 새 상수 파일(`tem_versions.js` 류)을 만들지 않는다 — 손으로 올리는 버전은 잊히고, 실제 값 스냅샷이 더 정직하다.

### 안 B — 실험 조건·사슬 열 3개 (같은 표)

| 열 | 형 | 채우는 법 | 없을 때 |
|---|---|---|---|
| `condition_id` | text | URL `?cond=<이름>` → 회차 시작 시 provenance에 기록. 실험자가 링크로 배포(알파 초대 방식 그대로) | null |
| `chain_id` | uuid | URL `?chain=<uuid>` 동일 | null |
| `parent_run_id` | uuid | (i) URL `?after=<run_id>` 또는 (ii) 자동: 같은 브라우저 localStorage의 직전 run_id | null |

셋 다 provenance jsonb 안에 넣어도 되지만, **조회·조인 대상**이라 별도 열이 낫다(사슬별 집계는 jsonb 경로 인덱스보다 열 인덱스가 단순).

RECORD 경로의 사슬 연결은 따로: `memories.meta.record_v4.parent_memory_id` — 재서술이 어느 기억을 보고 왔는지. recordPlay는 직전 플레이 기억을 localStorage로 알 수 있으므로 자동 채움 가능. **H2(노출-선택적 보존) 검정의 전제.**

### 안 C — 하지 말 것

- plays에 열 추가(씬마다 중복). 
- 실험 전용 새 표 6개·Edge 4개(생애그릇 §8 문제 ③ 판례 — 5장면·1유령·3관객에 그 규모는 과잉).
- Edge 함수마다 버전 스탬프(record-erosion·record-contamination 등에 각각) — 한 곳(run_journals)이면 충분하고, Edge는 service_role이라 잘못 쓰면 되돌리기 어렵다.

## 4. 예측값 표 — 지금 만들지 않는다

원문 §6 "모델 예측(model_version, 예측값)" 자리는 인지·전승 모델이 **아직 없다**. 모델 없이 표부터 만들면 연구 프로그램 R3(정의 미완 상태의 데이터 축적)를 그대로 반복한다. 첫 가설(Q3) 확정 뒤 1표: `model_predictions(run_id, model_version, target text, predicted jsonb, created_at)`. 설계만 여기 적어 둔다.

같은 이유로 `analysis_version`도 표가 아니라 **분석 스크립트 출력 파일의 머리**(tools/ 결과 JSON 첫 키)에 둔다 — 지금 페르소나 리트머스·C2 결과가 하는 방식 그대로.

## 5. 튜닝 절차 (안 A가 들어간 뒤)

1. 손잡이를 바꾸는 커밋마다 `docs/이본지층/손잡이_이력.md`에 (날짜, 키, 전→후, 근거, 배포 시각) 한 줄 append.
2. 배포 뒤 첫 회차의 provenance를 열어 값이 바뀐 것을 **눈으로 확인**(캐시버스터 갱신 검증을 겸함 — [[feedback_cachebuster_on_edit]]).
3. 과거 행(안 A 이전)은 §2 표대로 소급 라벨을 분석 스크립트가 붙인다 — DB는 안 건드린다.
4. `terrain_layers`는 캐시이므로 손잡이가 바뀌면 `rebuildFromPlays`가 **다른 땅**을 만든다. 튜닝 전 스냅샷(Storage)을 "w1-6 최종"으로 표시해 보존.
