## 0. 한 줄 문제

TEM 안에 감정을 담는 "칸(축)"의 정의가 **네 벌** 있고, 그 사이를 옮겨주는 변환 코드가 **한 줄도 없다.** 그래서 관객이 "그리움(longing)"으로 기억을 읽어도 정렬도 점수에 **1도 반영되지 않는다.** 실제로 점수에 기여하는 축은 네 벌의 교집합 **9칸뿐**이다.

**변환 함수: 존재하지 않음 (grep 0건).**

### 1.1 교집합 — 실제로 점수에 기여하는 축

- **A ∩ B (판단↔생산) = 공통 9축**: `fear, sadness, anger, joy, guilt, shame, numbness, isolation, relief`
- **A에만 (생산이 안 만드는 8축)**: `moral_pain, helplessness, despair, hope, gratitude, love, peace, comfort` → AI가 절대 안 내보내므로 **판단에서 항상 0**
- **B에만 (판단이 안 보는 3축)**: `longing, confusion, emptiness` → AI가 만들지만 코사인이 **통째로 무시**

즉 AI가 12칸으로 감정을 뽑아도, 판단하는 자는 그중 9칸만 읽고 3칸(그리움·혼란·공허)은 버린다. 그리고 판단자가 준비한 8칸(도덕적고통·절망·희망·사랑 등)은 생산자가 절대 안 채워서 늘 빈칸이다.

### 1.2 왜 이게 아픈가 (파급)

1. **작품 핵심 정서가 점수 밖.** `longing`(그리움)은 echo_words·되새김·작품 주제어의 중심인데 정렬도에 미반영. `emptiness`(공허)는 "당신의 음각은 어디에 새겨져 있는가"의 정서적 바닥인데 역시 미반영.
2. **지형이 감정의 절반을 못 본다.** 지형 배치(`estimateAFFromEmotion`)가 쓰는 C축 표에 A의 9축(moral_pain·helplessness·despair·hope·gratitude·love·peace·comfort)이 키로 없어 `if(!mapping) continue`로 버려진다(`tem_af_map.js:163`).
3. **같은 DB 컬럼에 3벌 스키마 공존.** `scenes.original_emotion`이 8축·12축·문자열로 섞여 저장돼 있다(L3 실측: 문자열 26행, 키셋 최소 6종). admin 편집기는 17축, Canvas는 8축으로 같은 컬럼을 이중 편집한다(F4).

> 참고: shape(궤적 유사도)는 R4-1(2026-07-14)로 판단 정본 A(17축)에 정렬됨 — 이전엔 22축(유령 키 grief/tenderness 포함)이었다. 따라서 지금 level과 shape는 **같은 A축**을 쓴다. 남은 균열은 **생산(B)↔판단(A)** 과 **판단(A)↔지형(C)** 두 곳.

## 2. 통합안 3안

세 안 모두 목표는 같다: **생산·판단·지형이 같은 축을 쓰게 한다.** 다른 것은 "어느 축으로 통일하느냐"와 "기존 데이터를 어떻게 하느냐"다.

### A안 — 생산을 판단 17축으로 확장

생산측(Edge 프롬프트·SeekerFingerprint·admin·drift)을 판단 정본 A(17축)에 맞춘다. AI가 앞으로 17칸으로 감정을 뽑는다.

- **바뀌는 것**: `longing/confusion/emptiness`가 생산에서 **사라지고**, 대신 `moral_pain/helplessness/despair/hope/gratitude/love/peace/comfort`가 새로 생산된다.
- **기존 데이터**: 그대로 두면 12축이라 새 8축은 0. 마이그레이션 불요(근사 열화만).
- **치명적 손실**: **그리움·공허가 스키마에서 퇴출된다.** TEM 정서의 중심 두 축을 버리는 셈. → 작품 정체성과 충돌.

### B안 — 12축은 그대로, 판단 직전에 12→17 매핑 함수

생산·저장은 B(12축) 유지. 판단 코사인에 들어가기 직전에 12축을 17축으로 옮기는 변환 함수 하나를 끼운다.

12축 중 판단에 없는 3축을 A의 축으로 보내는 **매핑표 초안**:

| 생산 축(B) | 판단 축(A)으로 | 근거 |
|---|---|---|
| longing | → **despair 0.3 + sadness 0.4** (또는 신규 축 유지) | 그리움 = 상실 지향 슬픔. 단 뭉개면 그리움≠슬픔 왜곡 |
| confusion | → **helplessness 0.5** | 혼란 = 통제 상실감 근접 |
| emptiness | → **numbness 0.6 + despair 0.3** | 공허 = 저각성 마비+절망 |

- **바뀌는 것**: 코드 한 함수 추가(`mapProductionToJudgment(vec12) → vec17`). 생산·저장·프롬프트 **불변**.
- **기존 데이터**: **마이그레이션 불요** (읽을 때 변환). 가장 안전.
- **롤백**: 함수 하나 제거하면 원상복구. 가장 쉬움.
- **약점**: 매핑이 **정보 왜곡**. 그리움을 슬픔+절망으로 뭉개면 "그리움만의 결"이 사라진다. 위 계수는 초안일 뿐, 확정하려면 작가 판단 필요.

#### B′안 (권고 — B의 무손실 변형)

3축을 억지로 A로 뭉개지 말고, **판단 정본을 A(17) → A+3(20축)으로 확장**한다. `longing/confusion/emptiness`를 판단 코사인 keys에 그대로 추가.

- 생산(12축) 물의 **12칸 전부**가 판단에 기여(공통 9 + longing/confusion/emptiness 3).
- A 고유 8축(moral_pain 등)은 생산이 안 만들면 0이지만, admin/작가가 17축+ 입력할 때 채워짐(현행 admin은 이미 이 8축 일부 입력 가능).
- 사실상 **C안의 최소 버전** — 신규 VAD 좌표 없이 판단축만 확장.

### C안 — 20축 신정본 (17 + longing + confusion + emptiness)

생산·판단·지형·저장 **전부** 20축으로 통일. 가장 표현력 크고 가장 큰 공사.

- **바뀌는 것**: Edge 프롬프트·SeekerFingerprint·math.js·tem_af_map(VAD 좌표 3축 신설)·tem_geo_map·admin UI 전부.
- **기존 데이터**: `ghost_variants.emotion_vec`(197행)·`scenes.original_emotion`·`plays` 벡터를 **재추출/재계산**하는 마이그레이션 필요.
- **롤백**: 어려움(스키마·프롬프트·데이터 전방위).

### 3.1 지형(A↔C) 균열은 어느 안에서도 별도 작업

A↔C(판단↔지형)는 위 3안(생산↔판단)과 **독립**이다. C의 제3의 17축(Plutchik 계열: resentment·contempt·anxiety 등)은 판단축 어디에도 없다. B′/A/B 어느 걸 골라도 지형 균열은 남으며, 별도로:
- (ㄱ) `tem_af_map.js`의 축 표에 A(또는 20축)의 누락 9축 VAD 좌표를 추가하거나,
- (ㄴ) 지형 입력 직전에 판단축→AF 매핑 함수를 끼운다.
죽은 `tem_af_analysis.js`(소비처 0, L5-17)는 이 기회에 삭제 권장.

## 4. 권고

**B′안 (판단 정본을 17→20축으로 확장).**

이유:
1. **작품 정체성 보존이 최우선.** longing(그리움)·emptiness(공허)는 TEM의 정서적 중심이다. A안(퇴출)·B안(뭉갬)은 이 결을 훼손한다. B′만 원형을 지킨다.
2. **비용 대비 효과 최대.** 변경은 `math.js`의 상수 1곳(+선택적으로 tem_geo_map에 3축 VAD 좌표). 데이터 마이그레이션 불요, 롤백은 상수 되돌리기.
3. **C안의 표현력을 사실상 얻으면서 공사비만 줄인다.** A 고유 8축(moral_pain 등)은 지금도 생산이 안 만드니 20축이든 17축이든 실사용 축은 12+admin 입력분으로 같다.

**단, 최종 결정은 기억유전학 정본이다.** 만약 "moral_pain·despair·love 같은 회복/도덕 축을 AI가 적극 생산해야 한다"가 작품 방향이면 → C안(20축 전면)이 맞다. "그리움은 슬픔의 하위다"라는 이론적 판단이 서면 → B안(매핑)도 가능. 이 문서는 **셋 다 열어두고 B′를 기본 권고로** 올린다.

### 4.1 어느 안이든 함께 처리할 것

- `scenes.original_emotion` 문자열 26행(L3) — 객체로 정규화(파서 의존 제거).
- admin 8축(D)과 Canvas 8축 이중 편집(F4) — 선택한 정본축으로 단일화.

## 5. (R4-6) avoidance·contradiction 기하 대안 — SceneNavigator

> `js/core/SceneNavigator.js`. **이 절도 제안이다. 코드를 바꾸지 않는다.** 서사 동작(어느 씬이 다음에 열리나)이 바뀌는 사안이라 결정이 먼저다. 참고: [L5-11]·[L5-12].

원칙 1(CLAUDE.md §6.5 #1): *"패턴은 접근 공간의 중심을 이동시킨다(GEOMETRY), 반경만 X."* 6패턴 중 **두 패턴의 중심 정의가 실질적으로 무의미**하다.

### 5.1 avoidance — 빈 벡터가 "배열 첫 씬"을 고른다

**현재**(`:120~122`): `mode:'void'` → `return {}`. 중심이 빈 객체 → 모든 씬 코사인 ≈ 0 → radius 미달 → fallback → `scored[0]`(후보 배열 **첫 원소**) 반환. 설계 의도("void/neutral 영역 유도")와 달리 **감정과 무관한 배열 순서 선택**이고 fallback 서사 문구가 매번 뜬다.

**대안**: 빈 벡터 대신 **저각성·중립 앵커 벡터**를 중심으로. 회피 = "감정을 끄는 쪽으로 유도"이므로, 저각성 마비/공허 축에 약한 가중을 준 실제 벡터:
```
avoidanceCenter = normalize({ numbness: 0.5, emptiness: 0.4, isolation: 0.3 })
```
→ 코사인이 실제로 "감정이 잦아든 씬"을 고른다. fallback이 아니라 정상 경로로 회피 씬 선택. (정본축이 20축(B′)이면 emptiness가 판단에 살아있어 이 벡터가 바로 작동한다 — 축 통일과 맞물리는 지점.)

### 5.2 contradiction — 보수(1−x)가 균일 벡터를 만든다

**현재**(`:154~159`): `_negateEmotion` = `result[k] = 1 - (emotion[k]||0)`. 감정 벡터는 희소(대부분 0)라 `1−0=1` → **거의 모든 축이 1인 균일 벡터** → 모든 씬과 코사인이 엇비슷 → 변별력 상실. "유저 감정의 OPPOSITE"(§6.5 #1)가 아니라 "모든 감정의 평균 쪽".

**대안 두 갈래** (택1은 작가 판단):
- **(가) 지배축 반전 + 정규화**: 유저의 지배 감정축(argmax)만 잡아, VAD 상 그 반대편 앵커로 중심을 옮긴다. 예: 유저 지배=fear → 중심 = fear의 VAD 반대 앵커(relief/peace 쪽) 가중. "정반대 감정"의 문자적 구현.
- **(나) 지배축 소거 + 정규화**: 유저 지배축만 0으로 누르고 나머지는 유지 후 정규화. "그 감정만 회피"(반전보다 온건). 균일 벡터 문제를 피하면서 서사적으로 덜 급격.

두 대안 모두 희소 벡터에서 균일화가 일어나지 않는다. **어느 쪽이 TEM 서사에 맞는지는 작가 결정** — (가)는 극적 반전, (나)는 미묘한 이탈.

### 5.3 주의

avoidance는 현재 [L5-02](VOID 미도달)로 애초에 발생하지 않고, contradiction은 MID 지배([L5-06])로 드물다. 즉 **이 두 대안은 A2/A3(오염 사슬 입력)·L5-02(VOID 배선) 수리가 선행돼야 실효**가 있다. 그 전에 SceneNavigator만 고치면 검증할 입력이 없다. 수리 순서상 **오염 사슬 복원 이후**로 미루는 게 맞다.

## 6. 남은 결정 (사장님께)

1. **정본 축**: B′(20축, 권고) / A(17축, 그리움 퇴출) / B(매핑) / C(20축 전면 재추출) 중 택1.
2. **B/B′ 선택 시 매핑 계수**: §2 B안 표의 longing·confusion·emptiness 처리(뭉갤지 원형 보존할지).
3. **지형(C축) 균열**: §3.1 (ㄱ) VAD 좌표 추가 vs (ㄴ) 매핑 함수 — 정본 축 결정 후.
4. **contradiction 기하**: §5.2 (가) 반전 vs (나) 소거.

이 넷이 정해지면 별도 수리 레인이 구현한다. 그 전까지 코드는 R4-1(shape 17축 정렬)에서 멈춘다.
