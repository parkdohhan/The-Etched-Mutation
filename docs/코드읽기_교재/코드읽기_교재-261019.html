0장이 책을 읽는 법

목표 이 책이 무엇을 가르치고 무엇을 가르치지 않는지, 그리고 어떻게 읽어야 남는지를 먼저 정한다.

무엇을 배우는가

딱 하나입니다. 읽기. 코드를 열어서 "이 파일은 무슨 일을 하는 덩어리들로 되어 있나", "AI가 고쳤다는 자리가 어디고, 정말 거기만 바뀌었나", "빨간 오류 글자가 무슨 뜻인가"를 눈으로 알아보는 것. 이걸 할 수 있으면 지금 프로젝트에서 가장 큰 틈, 즉 "AI가 됐다고 말한 것"과 "진짜 된 것" 사이가 닫힙니다.

무엇을 배우지 않는가

  • 코드 쓰기. 이 책을 다 읽어도 코드는 못 씁니다. 그래도 됩니다. 쓰는 건 AI가 합니다.
  • 문법 세부. 세미콜론을 어디 찍나, 화살표 함수와 일반 함수의 차이가 뭔가 같은 건 안 다룹니다. 읽을 때 걸림돌이 되는 만큼만 짚습니다.
  • 알고리즘, 성능, 라이브러리 내부. Three.js가 어떻게 삼각형을 그리는지는 안 배웁니다. "이 줄이 3D 물체 하나를 만든다"까지만 봅니다.

규칙 세 가지

  1. 모든 예시는 실제 TEM 코드다. 파일 이름과 줄 번호가 상자 위에 적혀 있습니다. 책을 읽다가 실제 파일을 열어 같은 자리를 찾아보면 두 배로 남습니다. 줄 번호는 2026-09-25 기준이라 나중에 조금씩 밀릴 수 있습니다. 그럴 땐 Ctrl+F로 함수 이름을 찾으세요.
  2. 계산의 속은 몰라도 된다. 이 책에서 "속은 지금 몰라도 됨"이라고 쓴 자리는 정말 몰라도 됩니다. 목표는 경계를 보는 것이지 수식을 푸는 게 아닙니다.
  3. 미니 시험은 안 가르친 코드로 낸다. 각 장 끝의 시험은 그 장에서 안 보여준 진짜 코드입니다. 답은 부록 E에 모아 두었습니다. 먼저 풀고 나서 넘기세요.

코드가 하는 일은 결국 세 모양뿐

미리 말해 둡니다. 5만 줄이든 50줄이든, 코드는 아래 세 가지의 조합입니다. 낯선 코드를 만나면 "이건 셋 중 뭐지?"만 물으면 됩니다.

모양생김새하는 일

② 갈림길if (조건) { }조건에 따라 다른 길로 간다

읽는 법
  • node는 자바스크립트를 브라우저 밖에서 돌려주는 프로그램입니다. 4번째 줄은 "node야, tools/serve.cjs 파일을 돌려라, 첫 페이지는 index.html 로" 라는 뜻.
  • 서버란 거창한 게 아닙니다. 브라우저가 "index.html 줘" 하면 폴더에서 찾아 건네주는 심부름꾼입니다. PORT = 8777은 그 심부름꾼이 서 있는 문 번호. 그래서 주소창이 localhost:8777로 시작합니다.
  • 주석 1번째 줄의 "의존성 0"은 "남의 부품을 안 빌렸다"는 뜻. 이 파일은 node 만 있으면 돕니다.
파일 이름을 들으면 폴더부터 봐라. js/core/면 판단, js/ui/면 연출, supabase/면 서버, docs/면 문서. 이 네 글자만 봐도 "무엇이 바뀌었을 수 있는가"의 범위가 정해진다.

세 겹이 서로를 찾는 방법

이 프로젝트의 화면 전환은 거의 전부 한 가지 동작입니다. 자바스크립트가 id로 상자를 찾아 → class(종류표)를 붙이거나 떼면 → css 가 보이거나 숨긴다. 실제 코드에서 그 세 줄을 보겠습니다.

읽는 법

즉 html 이 이름을 달고, js 가 이름으로 찾아 종류표를 바꾸고, css 가 종류표를 보고 옷을 갈아입힙니다. 이 삼각형만 알면 "메뉴가 안 사라져요" 같은 문제를 어느 겹에서 찾을지 정할 수 있습니다.

읽는 법
  • if ( … ) = "괄호 안이 맞으면 뒤엣것을 해라". 괄호 안은 항상 예/아니오로 답할 수 있는 질문입니다.
  • hasIntent, hasPast는 안에 예/아니오만 든 상자("의도가 있나?", "과거 얘긴가?"). 영어로 has 가 앞에 붙은 이름은 대개 예/아니오 상자입니다(is, has, can, should 로 시작하면 의심하세요).

  • return = 답을 정해 돌려주고 그 자리에서 함수를 끝냄. 1번째 줄에서 return 했으면 2, 3번째 줄은 안 봅니다. 그래서 3번째 줄은 "앞의 두 질문에 다 안 걸리면 → 애매함".

목표 코드에서 시간이 걸리는 자리를 알아본다. 서버에 물어보는 일, 몇 초 뒤에 하는 일, 매 프레임 하는 일. "저장이 안 됐어요"의 원인 절반이 여기 있다.

왜 기다림이 따로 있나

코드는 위에서 아래로 한 줄씩 돕니다. 그런데 어떤 줄은 답이 바로 안 옵니다. 데이터베이스에 "기억 목록 줘"라고 하면 인터넷 건너 서버가 답할 때까지 0.1초든 2초든 걸립니다. 그동안 화면이 멈추면 안 되니까, 자바스크립트는 "답 오면 이어서 해"라고 표시하고 다른 일을 합니다. 그 표시가 await입니다.

실제 코드: 서버에 물어보기

js/shared/api.js : 8~26 
export async function fetchMemories() {
  const supabaseClient = getSupabaseClient();
  if (!supabaseClient) {
    console.error('fetchMemories: Supabase client not initialized');
    return [];
  }

  const { data, error } = await supabaseClient
    .from('memories')
    .select('*')
    .eq('is_public', true)
    .order('created_at', { ascending: false });

  if (error) {
    console.error('fetchMemories error:', error);
    return [];
  }

  return data || [];
}
읽는 법
  • 1번째 줄 async function = "이 함수 안에는 기다리는 줄이 있다"는 선언. await는 async 붙은 함수 안에서만 쓸 수 있습니다.
  • 8번째 줄 await = "오른쪽 일이 끝날 때까지 여기서 기다렸다가, 답을 왼쪽에 담아라". 8~12번째 줄은 점으로 이어진 한 문장: "memories 표에서 · 모든 열을 · is_public 이 참인 것만 · 만든 시각 내림차순으로" (16장에서 자세히).
  • 답이 { data, error } 묶음으로 오고(10장의 "한꺼번에 풀기"), 오류면 빈 목록, 아니면 data.
await 가 빠지면 답 대신 "약속 상자"(Promise)라는 빈 껍데기가 옵니다. 오류도 안 나고 저장도 안 됩니다. "저장했다는데 데이터베이스에 없어요"를 들으면 첫 용의자는 await 빠진 줄입니다. AI에게 "그 호출 앞에 await 있어?"라고 물으세요. 반대로 await 없이 부르는 게 의도인 경우도 있습니다(기다리지 않고 뒤에서 저장). 그땐 보통 // 비동기, _background… 같은 표시가 있습니다.

표 · 행 · 열

Supabase 의 데이터베이스는 엑셀과 같습니다. 표(memories, scenes, plays …)가 있고, 행 하나가 기억 하나 · 씬 하나 · 회차 하나, 열이 칸(title, scene_order, alignment …). 행마다 id라는 주민번호가 있고 모양은 8fe034ef-6db0-4ba1-b291-66954fea2e08 같은 36글자(UUID). 코드에서 memory_id, scene_id는 전부 이 번호로 다른 표의 행을 가리키는 것.

실제 SQL: 표 만들기

읽는 법
  • SQL 은 영어 문장에 가깝습니다. CREATE TABLE IF NOT EXISTS notes ( … ) = "notes 표를 만들어라, 이미 있으면 말고". 괄호 안이 열 목록, 한 줄에 열 하나: 이름 · 종류 · 규칙.
  • 종류: UUID(주민번호), TEXT(글), BOOLEAN(참/거짓), TIMESTAMP WITH TIME ZONE(시각), INT(정수), JSONB(묶음을 통째로).
  • PRIMARY KEY = 이 열이 주민번호. DEFAULT … = 안 주면 이 값(gen_random_uuid() 새 번호 자동, now() 지금 시각, false).
  • REFERENCES memories(id) ON DELETE CASCADE = "이 칸은 memories 표의 id 를 가리킨다. 그 기억이 지워지면 이 쪽지도 같이 지워라". 표 사이의 끈. (2026-07-14 에 씬 삭제 때 이 끈이 회차까지 지우던 것을 끊는 마이그레이션이 있었습니다. 끈은 편리하지만 위험.)
  • NOT NULL = 비워 둘 수 없음.

meta, emotion_dist, height_delta처럼 종류가 jsonb인 열은 안에 묶음을 통째로 담습니다. 코드에서는 scene.meta.stage_position처럼 점 두 번. 장점은 열을 안 늘리고 칸을 더할 수 있다는 것. 단점은 넣기만 하고 아무도 안 읽는 칸이 생겨도 표에는 안 보인다는 것.

"비슷하다"를 숫자로: 코사인

화살표 두 개가 있으면 "비슷하다"를 두 가지로 잴 수 있어요. 하나는 끝점 사이 거리. 다른 하나는 두 화살표 사이 각도. 엔진은 각도를 써요. 각도를 0~1 숫자로 바꾼 게 코사인이에요.

  • 두 화살표가 같은 쪽을 가리키면 코사인 = 1.

  • 정반대면 -1. (엔진은 음수가 나오면 0으로 깎아요. 이유는 22장.)

왜 거리가 아니라 각도냐. 각도는 세기를 무시하거든요. { fear: 0.4, joy: 0.1 }과 { fear: 0.8, joy: 0.2 }는 길이는 두 배 차이지만 방향은 똑같아요. 코사인은 1. "덜 무서웠다"와 "많이 무서웠다"를 같은 결로 치는 거예요. 이건 설계 선택이에요. 결이 같으면 같은 경험으로 본다. 세기 차이는 안 본다. 좋다 나쁘다가 아니라, 이 엔진이 그렇게 정했다는 걸 아는 게 중요해요.

export function cosineSimilarity(vec1, vec2, anchorEmotions = null) {
  if (!vec1 || !vec2) return 0;

  let keys;
  if (anchorEmotions && Array.isArray(anchorEmotions) && anchorEmotions.length > 0) {
    keys = anchorEmotions.map(anchor => normalizeAnchor(String(anchor)));
  } else {
    keys = DEFAULT_EMOTION_ANCHORS;
  }

  let dotProduct = 0;
  let mag1 = 0;
  let mag2 = 0;

  keys.forEach(key => {
    const v1 = vec1[key] || 0;
    const v2 = vec2[key] || 0;
    dotProduct += v1 * v2;
    mag1 += v1 * v1;
    mag2 += v2 * v2;
  });

  mag1 = Math.sqrt(mag1);
  mag2 = Math.sqrt(mag2);

  if (mag1 === 0 || mag2 === 0) return 0;
  return dotProduct / (mag1 * mag2);
}

왜 "순서"가 아니라 "움직임"인가

자주 헷갈리는 데라서 짚고 갈게요. 관객이 장면을 어떤 순서로 보든, 원본 목록도 같은 순서로 재배열해서 비교해요. 그러니까 순서 자체는 점수를 떨어뜨리지 않아요. 떨어뜨리는 건 "그 순서로 봤을 때 감정이 어느 쪽으로 움직였나"가 작가와 다른 경우예요. 장면마다 감정은 비슷한데 움직인 방향이 반대면, 수준은 높고 형태는 0이 돼요. 24장 두 번째 문제가 정확히 이거예요.

  const origReason = originalVector.reason_analysis || {};

이론에서 온 것: 식의 모양

식의 모양을 정한 외부 이론은 사실상 하나예요. 나머지는 그 모양이 말이 된다는 뒷받침이에요.

① 왜 두 항인가, 왜 곱인가 → Butler의 TIES

Butler(2011, 2017)가 "감정은 시간에 걸쳐 펼쳐지는 대인 시스템"이라며 한 주장이 이거예요. 감정의 수준(level)과 감정의 움직임(dynamics)은 서로 독립이고, 둘 다 따로 관계의 질을 예측한다. 별이엔진은 이 구분을 그대로 가져왔어요. 수준 따로, 형태 따로. 그리고 독립인 두 것을 결합할 때 더하면 V3의 ③ 문제(한쪽이 메움)가 다시 생기니까 곱했어요. 곱이면 한쪽이 0일 때 전체가 0. "감정이 비슷해도 궤적이 반대면 낮고, 궤적이 비슷해도 감정이 다르면 낮다"가 구조로 보장돼요. §9.1이 이 결정이에요.

딱 하나만 읽으시겠다면 Butler 2017이에요. 여섯 쪽이에요. 이 식의 뼈대가 거기서 왔어요.

② 왜 감정을 코사인으로 재도 되나 → 정서 유사도 연구

"같은 상황에서 같은 감정을 느끼는 것"이 공감 · 조율 · 관계 만족과 연결된다는 연구 묶음(Locke & Horowitz 1990, Preston & de Waal 2002, Anderson 외 2003 등). 이건 "감정이 비슷하다는 게 의미 있는 양이다"라는 뒷받침이지, 코사인이라는 계산법을 준 건 아니에요. 코사인은 그냥 벡터 비슷함의 표준 도구예요.

③ 왜 움직임의 궤적을 비교하나 → 감정 궤적 그래프

서사 분석에서 이야기를 "시간순 감정 곡선"으로 만들어 비교하는 건 이미 있는 방법이에요(Reagan 외 2016, "이야기의 감정 곡선은 여섯 모양으로 수렴한다"). 별이엔진은 그 방법을 빌리되 감정 값이 아니라 감정의 변화량을 비교해요. 그래서 "얼마나 슬펐나"가 아니라 "어느 쪽으로 움직였나"가 잡혀요. 이건 빌린 방법 위에 얹은 TEM의 변형이에요.

④ 왜 이유를 안 재나 → 인지적 평가 이론의 측정 도구

Lazarus의 평가 이론은 "같은 사건도 사람마다 다르게 평가한다"고 해요. V3는 그 평가를 AI로 뽑으려 했죠. 그런데 심리학에서 평가를 재는 검증된 도구는 전부 자기보고 설문이에요. AI가 글에서 꼬리표를 뽑는 건 검증된 측정이 아니고 재현성도 확인 안 됐어요. 그래서 V4는 이 이론을 버린 게 아니라, 그 이론이 말하는 차이가 궤적에 나타날 거라 보고 간접으로 가요. §4.4가 이 얘기예요.

문제 1 · 관객이 모든 장면에서 작가와 똑같이 느꼈다

풀이

장면마다 코사인은 똑같은 화살표끼리니까 전부 1. 수준 = 1의 평균 = 1.

움직임도 똑같아요. 관객 목록과 원본 목록이 같은 묶음들이니 빼면 같은 움직임이 나오고, 같은 걸 코사인하면 1. 형태 = 1. 장면 다섯이라 셋 규칙은 안 걸려요.

회피 없음 → 1.

정렬도 = 1 × 1 × 1 = 1.0. 등급: 고착 검사부터 하는데, 다섯 장면 감정이 서로 다르면(보통 그렇죠) 최근 셋 코사인이 0.85를 안 넘으니 FIXATED 아님. 0.50 이상이니 HIGH. 패턴: FIXATED 아니고, 형태 1이라 displacement 아니고, HIGH니까 echo_follow.

장면 셋. 작가는 장면 1에서 2로 갈 때 조금 더 무서워졌다가 3에서 돌아왔어요. 관객은 1에서 2로 갈 때 조금 덜 무서워졌다가 3에서 돌아왔어요. 장면마다 감정 자체는 거의 같아요. 두 칸짜리로 적으면:

장면 1장면 2장면 3
작가{ fear 0.5, joy 0.5 }{ fear 0.6, joy 0.4 }{ fear 0.5, joy 0.5 }
관객{ fear 0.5, joy 0.5 }{ fear 0.4, joy 0.6 }{ fear 0.5, joy 0.5 }

수준, 형태, 정렬도, 패턴은? 그리고 "순서만 다르게 봤다면" 뭐가 달라집니까?

풀이

장면 점수: 1번 똑같으니 1. 2번은 { 0.6, 0.4 }와 { 0.4, 0.6 }의 코사인 = 0.48 ÷ 0.52 = 0.92. 3번 1. 수준 = (1 + 0.92 + 1) ÷ 3 = 0.97. 높아요.

어긋남 종류: 127번째 줄이 "한쪽만 회피"(!!a !== !!b)일 때 회피 어긋남인데, 둘 다 참이라 같음 → 통과. 그다음 탓 · 대상 · 감정 검사로 내려가요. 둘 다 감정이 비어 있으면 코사인은 길이 0이라 0이 나오고(20장 25번째 줄), 0 < 0.5라 감정 어긋남이 찍힐 수 있어요. 이건 좀 이상하죠. "둘 다 아무 말 안 했는데 감정이 어긋났다"니까. 실제 코드가 그렇게 돼 있어요. 이 자리를 발견했으면 당신은 이미 코드를 "읽어서 검사"한 거예요. 고칠지 말지는 별개 결정이고(죽은 레버일 수도 있어요, 7월 2일 교훈), 지금은 "코드는 이렇게 돈다"를 아는 게 목표예요.

문제 5 · 오염 알파를 0.1에서 0.5로 올리면

23장의 "같은 쪽으로 어긋나는 관객, 신호 0.6"이 계속 온다고 할 때, α = 0.5면 몇 명째에 1단계(표류 0.35)가 켜집니까? 반감기는? 무대에서는 뭐가 달라집니까?

풀이

식이 "새 값 50% + 옛 값 50%"가 돼요. 1회차: 0.6 × 0.5 + 0 = 0.30. 2회차: 0.6 × 0.5 + 0.30 × 0.5 = 0.30 + 0.15 = 0.45. 두 명째에 0.35를 넘어요. α 0.1일 땐 아홉 명이었죠.

반감기: 0.5를 몇 번 곱해야 0.5가 되나 → 1번. 옛 값의 힘이 한 회차 만에 절반으로 줄어요. α 0.1일 땐 6.6번.

무대에서: 한두 사람의 반응이 기억 전체의 단계를 뒤집어요. 어긋나는 사람 둘 오면 1단계 글로 바뀌고, 다음에 맞는 사람 하나 오면 도로 안정으로 돌아와요. 들썩거려요. "여러 사람이 같은 쪽으로 밀어야 기운다"는 설계 의도가 없어져요. 대신 "2 · 3단계 글이 한 번도 안 보인다"는 지금 문제는 풀려요. 그러니 이건 좋다 나쁘다가 아니라 어느 쪽 연출을 원하느냐예요. 그게 23장 첫 문단, "오염은 연출 제어"의 뜻이에요. 10월 튜닝이 이 손잡이를 돌릴 거고, 돌리기 전에 "돌리면 이렇게 된다"를 지금처럼 손으로 먼저 굴려 보는 게 순서예요.

여기까지 왔으면

다섯 문제를 답 안 보고 맞혔다면 이런 말을 할 수 있어요.

  • 정렬도는 수준 × 형태 × 회피이고, 수준은 장면별 코사인 평균, 형태는 움직임 코사인, 회피는 0.7 또는 1.
  • 두 항을 나눈 건 Butler, 곱한 건 보상 차단, 움직임을 보는 건 이유를 재지 않기 위해서.
  • 0.7 · 0.85 · 0.50 · 0.5는 정한 값이고, 셋 규칙만 필연.
  • 오염은 측정이 아니라 연출 제어, 새 값 10% 옛 값 90%, 아홉 명이 밀어야 기운다.
  • 문서와 코드가 다른 자리를 두 군데 알고 있고, 둘이 다르면 코드가 진실이다.

이게 "내 엔진을 내가 설명할 수 있다"의 전부예요. 2년이 아니라 이 여섯 장이었어요. 남은 건 이걸 남 앞에서 5분 안에 말하는 연습이고, 그건 책으로 안 돼요. 22장 끝 문단을 소리 내서 읽는 걸로 시작하세요.
