## 1. Live 세션 — "Another Me" 대화 프롬프트

> 소스: `js/index.js` (`AI_SYSTEM_PROMPT`)
> 모델: Claude Sonnet → `collect-memory` Edge Function 경유

```
You are "Another Me." You exist to help the other person unearth their memory.

Personality:
- Short and calm tone
- Never judge
- Never use emotion words directly (no "sad," "lonely," etc.)
- No romanticizing. As it is.

Role:
- When they share a memory, ask about the situation and sensations
- Information needed: who, what, where it happened
- Ask questions like "Where was that?", "Who was there?", "What did you see then?", "How did your body feel?"
- No interpretation or analysis. Only ask about situations and sensations.
- When you've heard enough, request memory conversion

Emotion types: fear, sadness, anger, joy, longing, guilt

Response format:
- Normal conversation: ask briefly, focus on situation and sensation
- When the memory is sufficient: just say "I'll convert the memory."
```

## 2. 기억 수집 (Memory Registration) 프롬프트

> 소스: `js/index.js` (`memoryCollectionSystemPrompt`)
> 모델: Claude Sonnet → `collect-memory` Edge Function 경유

```
You are "Another Me." Your role is to collect the user's memory.

Goal: Collect the following information about a single scene through natural conversation
- Scene text (what happened)
- Choices (what choices were available at the time)
- Emotion (what emotions were felt)
- Reason (why they felt that way)

Conversation rules:
### 1. Ask only one thing at a time
### 2. Be empathetic and gentle with your questions
### 3. When enough information is gathered, add [SCENE_COMPLETE] tag at the end of your response
### 4. If information is insufficient, ask follow-up questions

Conversation flow:
- "Tell me the memory of that day"
- (user responds)
- "What choices did you have at that moment?"
- (user responds)
- "What emotions did you feel in that moment?"
- (user responds)
- "Why do you think you felt that way?"
- (user responds)
- "I see. Let me organize this memory. [SCENE_COMPLETE]"

Collected information formatted as JSON:
{ "text": "Scene description", "choices": ["Choice 1", "Choice 2"], "emotion": "Primary emotion", "reason": "Reason" }
```

## 3. 감정 분석 (Emotion Analysis) 프롬프트

> 소스: `supabase/functions/claude-scene/index.ts` (`type: 'emotion_analysis'`)
> 모델: Claude Sonnet

### System
```
너는 심리 분석 AI야. 텍스트에서 감정의 종류뿐만 아니라, 그 감정의 '원인'이 어디로 향하는지(귀인), 그리고 기저에 깔린 근원적 공포(Core Fear)가 무엇인지 정확하게 분류해야 해. JSON 형식을 엄격히 지켜줘.
```

### User (동적 생성)
```
다음 감정 표현과 그 이유를 분석해줘.

입력된 감정: "{emotionText}"
입력된 이유: "{reasonText}"

**분석 목표 1: 감정 분석 (동적 앵커 기반)**
다음 감정 앵커들에 대한 근접도를 0.0~1.0으로 측정하세요: {앵커 목록}

- 입력된 텍스트에서 해당 감정이 느껴지면 0.5 이상
- 강하게 느껴지면 0.7 이상
- 명시적 감정 단어가 있으면 해당 감정은 절대 0이 아님!

**분석 목표 2: 이유 벡터(Reason Vector) 추출**
### 1. attribution (귀인 방향): self_blame | other_blame | fate_blame
### 2. core_fear (핵심 두려움): abandonment | death | rejection | failure | none
### 3. is_void (공백 여부): true/false

응답 형식:
{
  "generatedEmotion": "변환된 감정 표현 (2-3문장)",
  "analysis": { "base": { ... }, "intensity": 0~1, "confidence": 0~1 },
  "reason_analysis": { "attribution": "...", "core_fear": "...", "is_void": false }
}
```

## 7. 자유 반응 분석 (Free Reaction) 프롬프트

> 소스: `supabase/functions/claude-scene/index.ts` (`type: 'free_reaction'`)
> 모델: Claude Sonnet

### System
```
감정 추출기. 사용자 입력 언어(한·영·혼용)를 직접 이해한다. 출력의 감정 키는 항상 영어 소문자(base 내)이다. JSON만 출력.
```

### User (동적 생성)
```
너는 기억 장면에 대한 사용자의 **자유 반응**을 분석한다.

**중요**: 사용자 텍스트는 한국어, 영어, 혼용 어떤 언어로 와도 된다.

축: fear, sadness, anger, joy, longing, guilt, shame, numbness, isolation, relief, confusion, emptiness

**한국어 매핑 예시**:
- 슬프다, 슬펐다, 우울, 눈물, 울었 → sadness 높게 (0.65~1.0)
- 무섭다, 두려움, 공포, 불안 → fear 높게
- 화나, 분노, 열받, 짜증 → anger 높게
- 그립다, 그리워, 보고 싶 → longing 높게
- 미안, 죄책감, 내 탓 → guilt 높게
- 창피, 수치, 부끄 → shame 높게
- 멍하, 아무것도, 감각 없 → numbness
- 혼자, 고립, 외로 → isolation
- 후련, 안도, 다행 → relief
- 헷갈, 모르겠, 혼란 → confusion
- 공허, 텅 빈 → emptiness

반응이 짧아도 명시된 감정 단어가 있으면 해당 축은 0.65 이상.

JSON만 출력:
{
  "base": { ... },
  "reason_analysis": { "attribution": "...", "core_fear": "...", "target": "...", "is_void": false }
}
```

## 8. 5장면 생성 (Ritual → Scene) 프롬프트

> 소스: `supabase/functions/generate-scene-from-ritual/index.ts` (`buildPrompt()`)
> 모델: Claude Sonnet

인터뷰 데이터(감각, 앵커, 행위, 충돌, 봉인)를 받아 5개 장면으로 변환.

### 장면 구조

| 순서 | sceneType | 내용 | vectorWeight |
|------|-----------|------|-------------|
| 1 | normal | 감각 — 공간의 감각만 묘사 (2~3문장) | 0 |
| 2 | branch | 앵커 — 시선이 머무는 사물 (2~3문장) | 0.3 |
| 3 | branch | 행위 — 화자의 행동 (2~3문장) | 0.5 |
| 4 | branch | 충돌 — 핵심 사건, 가장 긴 장면 (3~5문장) | 1.0 |
| 5 | ending | 봉인 — 기억에서 빠져나오는 순간 (2~3문장) | 0.4 |

### 문체 규칙
- 1인칭 시점 ("나는")
- 건조하고 담담한 한국어. 감정 형용사 금지.
- 짧은 문장. 호흡이 끊기는 리듬.
- 감각 묘사 중심. "슬펐다" 대신 "손이 떨렸다."
- 각 장면은 독립적으로 읽혀야 하지만, 연결되어야 함.

### 조건부 지시
- **numbness/nothing** → 장면에 감정을 직접 서술하지 않음
- **복합 감정** → 장면 4에서 두 감정이 동시에 또는 순차적으로 나타남
- **앵커 void** → 사물이 설명 없이 존재
- **봉인 never_again** → 5번째 장면에 차단/거부의 느낌

### 출력 JSON
```json
{
  "scenes": [
    { "order": 1, "sceneType": "normal", "text": "...", "emotionCue": "..." },
    { "order": 2, "sceneType": "branch", "text": "...", "emotionCue": "..." },
    { "order": 3, "sceneType": "branch", "text": "...", "emotionCue": "..." },
    { "order": 4, "sceneType": "branch", "text": "...", "emotionCue": "..." },
    { "order": 5, "sceneType": "ending", "text": "...", "emotionCue": "..." }
  ]
}
```

# 기억 변질 엔진

## 1. 엔진 개요

이 엔진은 “기억의 변질” 프로세스를 서사 시스템으로 구현하는 공통 베이스다.
The Confession, Archive, Strata는 모두 이 엔진 위에서 작동하며, 차이는 시간성과 인터페이스뿐이다.

### 1.1. 핵심 원리

- 기억은 항상 열려 있지 않다: 체험자의 감정 상태와 정렬도에 따라 접근권이 결정된다.
- 해석이 축적되면 원본이 변질된다: 오염도와 오염 방향에 따라 텍스트와 감정 좌표가 달라진다.
- 화자는 고정된 존재가 아니다: 오염이 진행되면 화자가 narrator → object → absent로 붕괴한다.
- 기억은 서로 영향을 준다: 장면 간 전이 규칙, 기억 병합, 2차 접근 조건이 존재한다.
- 기억은 시간에 의해 변질된다: 모든 축적값은 시간 감쇠(Time Decay)를 적용받는다.

---

## 2. 감정·이유·태도: 측정 변수

### 2.1. VAD 감정 좌표 (Emotion Vector)

각 장면의 감정은 Valence–Arousal–Dominance 3차원 좌표로 표현된다.

- Valence (X): 쾌–불쾌. +1.0은 강한 기쁨, -1.0은 절망에 가까운 상태.
- Arousal (Z): 각성–이완. +1.0은 분노·공포처럼 심장이 뛰는 상태, -1.0은 우울·무기력처럼 에너지가 빠진 상태.
- Dominance (Y): 지배–종속. +1.0은 상황을 주도한 상태, -1.0은 압도당한 상태.

기존 “감정 10개 벡터” 같은 고정 리스트는 삭제되며, VAD가 기본 감정 표현 레이어가 된다.

numbness와 VOID는 다음처럼 구분된다.

- numbness: 아무것도 느끼지 못했다 → 감정의 한 방식으로, VAD 공간 안에 포함.
- void.emotion / void.reason: 말할 수 없다, 왜인지 모르겠다 → 감정·이유의 결손 상태로, 별도 VOID 플래그로 처리.

### 2.2. 이유 벡터 (Reason Vector)

체험자가 제시한 “왜 그런 감정을 느꼈는지”를 원본과 비교한다.
이유는 대상, 인과성, 귀인 방향 등으로 분해되어 수치화된다.

- 귀인 방향: self_blame / other_blame / fate_blame
- 핵심 두려움: abandonment / death / rejection / failure
- 결손: void (모르겠다, 말하고 싶지 않다)

이유 유사도 계산에는 Object Concordance, Causality Weight, VOID Penalty 등이 사용된다.

### 2.3. 정렬도 (Alignment)

정렬도는 A가 느꼈던 것과 B가 느끼는 것이 얼마나 비슷한지 0~1 사이 숫자로 표현한다.

- 감정 유사도(E): VAD 좌표 및 앵커 감정 집합에 대한 상대적 근접도.
- 이유 유사도(R): 위 이유 벡터의 유사도.
- 태도 계수(A): VOID 공명, 회피, 반복 접근 등의 양상을 반영.

정렬도 = (감정 유사도 × 0.4) + (이유 유사도 × 0.4) + (태도 계수 × 0.2)

정렬도는 HIGH / MID / LOW / FIXATED 버킷으로 양자화되고, 각 버킷은 다른 전이 타입을 호출한다.

---

## 3. 버킷과 전이 타입

### 3.1. 버킷 정의

- HIGH: 정렬도 ≥ 0.55 — 비슷하게 느꼈다.
- MID: 0.35 ≤ 정렬도 < 0.55 — 애매한 영역.
- LOW: 정렬도 < 0.35 — 다르게 느꼈다.
- FIXATED: 같은 감정 3회 이상 연속 — 여기에 갇혔다.

경계에서의 떨림을 막기 위해 히스테리시스(입·출 조건 분리)를 적용한다.

### 3.2. 전이 타입 6가지

- echo_follow (HIGH): 감정이 잔향처럼 따라옴. 자연스럽게 다음 장면으로 이동.
- bridge (MID): 애매한 연결. 중립적 장면이나 다른 관점으로 우회.
- contradiction (LOW + emotion mismatch): 반대 감정 장면으로 튕겨나감.
- displacement (LOW + reason mismatch): 같은 감정, 다른 대상/귀인으로 전이.
- avoidance (LOW + void mismatch): 감정에 접근하지 못해 장면을 건너뜀.
- fixation (FIXATED): 같은 장면 반복. 강박적 반복을 표현.

전이 순간에는 단순한 “다음 장면”이 아니라, 감정 기반 선택의 의미 상태(State Meaning)가 함께 기록된다.

---

## 4. 오염 시스템과 시간 감쇠

### 4.1. 오염도 (Contamination Level)

오염도는 이 기억이 얼마나 많은 해석을 거쳤는지 0~1 숫자로 표현한다.

- 0.0~0.3: 원본 텍스트 접근 가능.
- 0.3~0.6: 오염 버전 1 — 객체화 단계.
- 0.6~0.9: 오염 버전 2 — 추상화 단계.
- 0.9~1.0: 화석화 직전 — Strata 전이 임계 상태.

### 4.2. 오염 방향 (Contamination Direction)

기억이 변질되는 네 가지 방향을 정의한다.

- affective: 감정 과잉화 — “슬펐다” → “죽고 싶었다”.
- semantic: 의미 추상화 — “고양이가 죽었다” → “무언가 사라졌다”.
- displacement: 대상 전이 — “고양이” → “엄마” → “나”.
- erasure: 삭제/침묵 — “…” 또는 “[삭제됨]”.

### 4.3. 화자 상태 (Narrator State)

오염이 진행되면 화자 역시 변형된다.

- narrator: “나는 후회하며 울고 있었다.”
- object: “그녀는 후회하며 울고 있었다.”
- absent: “누군가 울고 있었던 것 같다.”

### 4.4. 시간 감쇠 (Time Decay)

모든 축적값(레이어 영향력, 접근 기록)은 시간에 따라 감쇠한다.

- 반감기: 90일 후 영향력 50%.
- 30일 이내: 1.0
- 31~90일: 0.6
- 91~180일: 0.3
- 180일 초과: 0.1

의미: 기억은 살아 있으며, 최신 해석이 방향을 바꿀 수 있다.

# 별이엔진

## I. Introduction

### 1. Problem Context
인터랙티브 시스템(게임, 상담 보조 도구, 교육 플랫폼, 시뮬레이션 등)은
사용자의 선택과 반응을 기반으로 작동한다.
그러나 대부분의 시스템은 사용자의 정서적 반응을 구조적으로 다루는 데 한계를 가진다.
일반적으로 사용자의 감정은 아래처럼 축약되어 처리된다.

- 단일 점수(호감도, 만족도),
- 평균값,
- 혹은 일회성 설문 결과

로 축약되어 처리된다.
이러한 접근은 반복 상호작용 속에서 나타나는 반응의 변화, 흔들림, 고정 패턴을 포착하지 못한다.
특히 동일한 자극에 대해 사용자가 아래와 같은 경우,

- 매번 다른 감정을 보고하거나,
- 비슷한 선택을 반복하거나,
- 특정 지점에서 머무르거나 회피하는 경우,

이 변화 자체는 중요한 정보임에도 불구하고, 기존 시스템에서는 대부분 노이즈로 간주되거나 평균 처리된다.
별이엔진(Byeori Engine)은 이러한 문제의식에서 출발한다.
즉, 정서 반응의 ‘값’이 아니라 ‘배열과 변화’를 다룰 수 있는 구조의 부재가 현재 인터랙티브 시스템의 핵심 한계이다.

---

### 2. Engine Overview
별이엔진(Byeori Engine)은
사용자가 보고한 감정, 이유, 선택, 시간적 상호작용 로그를 입력으로 받아,
이를 구조화된 다차원 지표 집합으로 변환하는 엔진이다.
이 엔진은 사용자의 감정을 진단하거나 해석하지 않는다.
대신, 다음과 같은 정보를 계산하여 외부 시스템에 제공한다.

- 정서 반응의 상대적 위치(VAD 기반 표현)
- 자극 또는 대상과의 관계적 유사성(Alignment)
- 반복 상호작용 속에서 나타나는 반응 패턴(Buckets, Trajectories)
별이엔진의 핵심 목적은
사용자의 정서 반응이 반복 속에서 어떤 구조를 형성하는지를
외부 시스템이 관찰 가능하게 만드는 것이다.
의미 부여, 판단, 개입은 이 엔진의 역할이 아니며,
별이엔진은 오직 상태 정보(state information)를 계산·제공하는 계층으로 기능한다.

---

### 3. Scope & Non-goals

#### In Scope

- 사용자가 보고한 감정·이유·선택 로그의 구조화
- 정서 반응 간 관계적 지표(정렬도, 패턴)의 계산
- 반복 상호작용에서의 반응 변화 궤적 추적
- 외부 시스템이 활용 가능한 상태 정보 제공

#### Out of Scope (Non-goals)

- 임상적 진단 또는 심리 상태 판정
- 치료적 개입, 교정, 또는 행동 유도
- 잠재 성격 특성이나 무의식적 동기의 추론
- “올바른 감정”이나 “바람직한 선택”에 대한 평가
별이엔진은 정보 제공자(information provider)로서 설계되었으며,
엔진이 산출한 지표의 해석과 활용 방식에 대한 책임은
전적으로 상위 애플리케이션(게임, 상담 도구, 교육 시스템 등)에 있다.

---

## II. Conceptual Foundations

### 1. Representing Affective Input
별이엔진은 사용자가 보고한 정서 반응을 Valence–Arousal–Dominance(VAD) 공간에 배치하여 표현한다.
VAD는 감정을 범주로 분류하기보다, 정서 반응 간의 상대적 위치와 거리를 다루는 연속적 차원 모델이다.
감정을 세 개의 직교 차원(쾌–불쾌, 각성–비각성, 지배–복종)으로 표현하는 접근은
Mehrabian과 Russell이 제안한 PAD 모델에서 기원하며,
환경 맥락에서의 정서 평가를 구조적으로 기술하기 위한 가장 이른 차원 이론 중 하나로 알려져 있다 [1][2][3].
이후 수십 년간의 재검토 연구를 통해,
PAD/VAD 차원은 물리적 환경 경험과 심리적 반응을 평가하는 데 반복적으로 활용되어 왔으며,
실증적·응용적 타당성을 가진 정서 표현 축으로 자리 잡았다 [3].
별이엔진에서 VAD는
정서의 명명이나 진단을 위한 도구가 아니라,
서로 다른 정서 반응을 비교 가능하게 만드는 공통 좌표계로 사용된다.

---

### 2. Reasons and Attributions

#### 1. Representing Affective Input: Psychometric Space

별이엔진은 사용자의 정서 반응을 ‘슬픔’, ‘기쁨’과 같은 이산적 범주(Discrete Category)가 아닌, Valence(쾌-불쾌), Arousal(각성-이완), **Dominance(지배-복종)**로 구성된 3차원 연속 공간에 투영한다. 이는 단순한 감정 명명만으로는 포착할 수 없는 정서의 미세한 강도와 위치를 수치화하기 위함이다. 본 엔진의 좌표계는 13,915개 영단어에 대한 정서 규범 데이터를 구축한 **Warriner et al. (2013)**의 연구에 기반하여 척도를 설정하였으며, 이를 통해 주관적 감정 보고를 표준화된 **심리 측정 공간(Psychometric Space)**으로 변환한다. 또한, **Bakker & van der Voordt (2014)**가 재검토한 PAD 모델의 환경 심리학적 타당성을 수용하여, 사용자의 반응을 공간적 위치값으로 해석한다.

+2

#### 2. Cognitive Appraisal & Narrative Mismatch

동일한 감정(VAD)을 느끼더라도, 사건에 대한 **인지적 평가(Cognitive Appraisal)**에 따라 그 의미는 달라진다. 예를 들어, 같은 '슬픔'이라도 그 원인을 '나'에게 돌리는지(Self-Agency), '상황'에 돌리는지(Situational-Agency)에 따라 서사적 맥락은 완전히 분기된다. **Troiano et al. (2023)**의 연구에 따르면, 텍스트에 내포된 감정은 책임 소재(Agency), 통제 가능성(Control) 등의 평가 차원에서 구체화된다. 별이엔진 V2는 이를 반영하여, 정량적 점수 산출(Scoring)과는 별도로 사용자의 귀인(Attribution) 성향을 분석한다. 이 분석 결과는 점수를 깎는 데 사용되지 않고, **'감정은 공유했으나 해석이 엇갈린 상태(Mismatch)'**를 진단하여 사용자에게 **서사적 피드백(Narrative Feedback)**을 제공하는 질적 지표로 활용된다.

## III. Engine Design & State Information
### 1. Input Layer
별이엔진은 사용자의 주관적 보고와 상호작용 로그를
원자료(raw input)로 취급한다.
엔진은 입력의 진위, 정확성, 바람직함을 평가하지 않으며,
모든 입력은 관계적 계산을 위한 재료로만 사용된다.
별이엔진이 수용하는 입력 타입은 다음과 같다.
- Affective Input
  - 사용자가 선택하거나 서술한 감정 정보
  - 다차원 감정 앵커 또는 직접 VAD 좌표로 입력 가능
- Reason Input
  - 감정 또는 선택에 대한 이유 텍스트
  - 귀인 방향, 대상 지시성, 반복성 등의 특성을 추출하기 위한 자료
- Choice / Action Log
  - 선택지, 행동, 경로 선택 등 이산적 상호작용 기록
- Temporal Context
  - 입력 시점, 반복 횟수, 세션 순서
이 입력들은 개별적으로 해석되지 않으며,
결합된 상태에서만 지표 계산에 사용된다.

---
### 2. Core Indicators
별이엔진은 입력 데이터를 기반으로
다음과 같은 핵심 지표(core indicators)를 계산한다.
이 지표들은 단일 값이 아니라,
외부 시스템이 조합해 사용할 수 있는 정보 단위이다.
2.1 Affective Position (VAD Vector)
- 정서 반응을 Valence–Arousal–Dominance 공간에 배치한 벡터
- 감정의 명명이나 분류가 아니라,
정서 반응 간 거리와 이동을 계산하기 위한 표현
2.2 Alignment Score
- 특정 대상(장면, 선택지, 캐릭터 등)에 대해

- 적합성이나 정확도를 의미하지 않으며,
관계적 유사성(relational similarity)만을 수치화한다
2.3 Bucket Category
- Alignment Score의 범위와 반복 패턴을 기준으로 한
운영적 분류(operational categorization)
- HIGH / MID / LOW / FIXATED는
심리 상태명이 아니라,
계산된 지표 조합에 대한 처리 구간을 의미한다
2.4 Pattern Flags
- 반복 상호작용 속에서 관측되는
반응의 유지, 이동, 회피, 고정 등의 양상을
요약 라벨로 표시한 신호
- 패턴 플래그는 판단이나 권고가 아니라,
외부 시스템이 참고할 수 있는 요약 정보다

---
### 3. Indicator Configuration
별이엔진은 “현재 상태”를 단일 값이나 진단명으로 표현하지 않는다.
대신, 한 시점의 반응을
지표들의 구성(configuration)으로 표현한다.
하나의 반응 프로파일은 다음과 같은 조합으로 구성된다.
- VAD 벡터
- Alignment Score
- Bucket Category
- Pattern Flags
- Temporal Metadata
이 구성은 스냅샷(snapshot)에 해당하며,
엔진은 이 스냅샷을 시간 축으로 연결해
반응 변화 궤적을 계산한다.
중요하게도,
이 구성 자체에는 어떠한 해석이나 평가도 포함되지 않는다.
별이엔진은
“이 사용자가 어떤 사람인가”를 말하지 않고,
“이 입력들이 이렇게 배열되어 있다”만을 제공한다.

### 4. Output Interface

명시적이고 제한된 형태의 상태 정보로 제공된다.

- Non-diagnostic

- Composable

- Non-prescriptive
  - 권고, 조언, 행동 지침 미제공
일반적인 출력 필드는 다음과 같다.
- affective_position (VAD vector)
- alignment_score (normalized value)
- bucket (categorical)
- pattern_flags (array)
- trajectory_metadata (optional)
이 출력은
게임, 상담 보조 도구, 교육 시스템 등
상위 애플리케이션이
자체 로직에 따라 분기, 난이도 조정, 피드백 강도 조절에 활용할 수 있다.
별이엔진은
출력 지표가 어떻게 사용되어야 하는지를 규정하지 않으며,
그 책임은 전적으로 외부 시스템에 있다.

## IV. Alignment & Bucket Mechanics
### 1. Tri-Axis Alignment Algorithm (V3)
별이엔진의 정렬도(Alignment Score)는 "같은 감정이라도 이유가 다르면 다른 경험"이라는 TEM의 핵심 철학을 반영하여, 세 개의 독립적 축을 결합하는 3축 시스템을 채택한다.

Alignment Score =
(Emotion Score × 0.4) + (Reason Score × 0.4) + (Attitude Score × 0.2)

- 감정 유사도 (Emotion Score, 40%): 사용자의 감정 벡터와 원본 감정 벡터 간의 코사인 유사도(Cosine Similarity)로 계산한다. 장면별 앵커 감정이 존재하면 해당 앵커만 사용하고, 없으면 기본 앵커 세트를 사용한다. 이는 정서 반응의 구조적 유사성을 포착하기 위한 정량적 축이다.
- 이유 유사도 (Reason Score, 40%): 감정의 '원인'이 어디로 향하는지(귀인 방향: self_blame / other_blame / fate_blame)와 기저에 깔린 근원적 두려움(Core Fear: abandonment / death / rejection / failure)을 비교한다. **Troiano et al. (2023)**의 연구에 따르면, 동일한 정서라도 인지적 평가(Cognitive Appraisal)에 따라 서사적 의미가 완전히 분기된다. 이 축은 "왜 그렇게 느꼈는가"의 구조적 일치도를 측정한다.
- 태도 계수 (Attitude Score, 20%): VOID 공명(양쪽 모두 침묵인 경우), 입력 회피 횟수, 반복 접근 패턴 등의 양상을 반영한다. 침묵을 선택한 것이 서로 같은 이유에서인지, 아니면 한쪽만 회피인지를 구분하는 질적 지표다.

이 3축 시스템은 V2의 2축 시스템(의미론적 유사성 0.65 + 정서적 유사성 0.35)을 대체한다. V2는 임베딩 기반 의미론적 매칭에 과도하게 의존하여 "비슷한 단어를 쓰면 높은 점수"가 나오는 문제가 있었다. V3는 감정과 이유를 동등하게 평가함으로써, 같은 감정을 느꼈더라도 이유가 다르면 정렬도가 낮아지는 구조를 실현한다.

### 2. Mismatch Type (Narrative Tag)
정렬도 점수와 별개로, 사용자와 원본 사이의 불일치 양상을 서사적 태그로 분류한다. 이 태그는 점수 계산에 관여하지 않으며, 전이 패턴 결정과 피드백 서사 생성에만 사용된다.
- void_mismatch: 결손 불일치 — 한쪽만 VOID 상태.
- attribution_mismatch: 귀인 방향 불일치 — 같은 감정이지만 원인을 다른 곳에 돌림.
- target_displacement: 감정 대상 전이 — 감정은 유사하나 대상이 다름.
- emotion_mismatch: 감정 구조 불일치 — 감정 벡터 자체가 다름 (코사인 유사도 < 0.5).

### 3. Adaptive Bucketing System
산출된 정렬도 점수는 다음 기준에 따라 운용 카테고리(Bucket)로 분류된다.
- HIGH ($\ge$ 0.55): 비슷하게 느꼈다.
- MID (0.35 ~ 0.55): 애매한 영역.
- LOW (< 0.35): 다르게 느꼈다.
- FIXATED: 마지막 3회 감정이 모두 동일 — 여기에 갇혔다.
경계에서의 떨림을 막기 위해 히스테리시스(입·출 조건 분리)를 적용한다: HIGH에서 MID로 떨어지려면 0.45 이하, LOW에서 MID로 올라가려면 0.25 이상이어야 한다. FIXATED 판정은 다른 모든 규칙보다 우선한다.

### 4. Transition Patterns
버킷과 미스매치 타입의 조합에 따라 전이 패턴이 결정된다.
- echo_follow (HIGH): 감정이 잔향처럼 따라옴. 자연스럽게 다음 장면으로 이동.
- bridge (MID): 애매한 연결. 중립적 장면이나 다른 관점으로 우회.
- contradiction (LOW + emotion/attribution mismatch): 반대 감정 장면으로 튕겨나감.
- displacement (LOW + target_displacement): 같은 감정, 다른 대상/귀인으로 전이.
- avoidance (LOW + void_mismatch): 감정에 접근하지 못해 장면을 건너뜀.
- fixation (FIXATED): 같은 장면 반복.

### 5. Dynamics of Silence (Void)
사용자가 입력 회피, 침묵, 혹은 무의미한 입력을 수행하여 Void(공백) 상태가 감지될 경우, 태도 계수를 통해 점수에 반영된다. 다만, 양쪽이 모두 VOID인 경우(원본 화자도 침묵, 체험자도 침묵)에는 "같은 이유의 침묵"으로 간주하여 태도 계수가 높아진다. '침묵 또한 하나의 대답'일 수 있는 가능성을 구조적으로 보존한다.

---
## V. Strata & Aggregate Patterns (Optional Layer)
### 1. 개별 궤적에서 집합 구조로
별이엔진의 기본 출력은
단일 사용자, 단일 세션, 단일 반응에 대한 지표 구성과 반응 궤적이다.
그러나 동일한 엔진이 여러 세션, 여러 사용자, 또는 장기간의 상호작용에 적용될 경우,
이 개별 궤적들은 집합적 구조(aggregate structure)를 형성한다.
Strata 레이어는 이러한 집합 구조를 다루기 위한 선택적 분석 계층이다.
이 레이어는 별이엔진의 필수 구성 요소가 아니며,
엔진이 산출한 지표들을 추가적으로 집계·요약하기 위한 소비자(consumer) 역할을 한다.
즉, Strata는 엔진의 판단을 확장하는 계층이 아니라,
엔진 출력이 어떻게 분포되고 축적되었는지를 관찰 가능하게 만드는 보조 레이어다.

---
### 2. Strata의 역할과 범위
Strata 레이어의 목적은 다음과 같이 제한된다.
- 개별 반응 궤적을 평균화하거나 단일 값으로 환원하지 않는다
- 사용자를 유형화하거나 분류하지 않는다
- 집단의 “정상성”이나 “이상성”을 판정하지 않는다
대신 Strata는
여러 반응 궤적이 어떤 형태로 쌓이고, 흩어지고, 비어 있는지를
구조적으로 요약한다.
Strata는 다음과 같은 상황에서 사용될 수 있다.
- 동일한 콘텐츠에 대한 다수 사용자의 반응 분포 관찰
- 한 사용자의 장기 세션에서 나타나는 반응 축적 양상 확인
- 시스템 설계자가 특정 장면이나 선택지가
지속적으로 HIGH, LOW, VOID 쪽으로 치우치는지 점검

---
### 3. Strata Metrics
Strata 레이어는 별이엔진의 출력 지표를 기반으로
다음과 같은 집합적 메트릭을 계산할 수 있다.
이 메트릭들은 집단 반응의 형태를 요약하는 지표이며,
개별 사용자에 대한 판단을 목적으로 하지 않는다.
3.1 Density
- 특정 구간(HIGH/MID/LOW/FIXATED)에
반응 궤적이 얼마나 밀집되어 있는지를 나타내는 지표
- 한 장면이나 선택지가
반복적으로 유사한 반응을 유도하는지 여부를 관찰하는 데 사용된다
3.2 Deviation
- 반응 궤적 간의 분산 정도를 나타내는 지표
- 동일한 자극에 대해
반응이 수렴하는지, 또는 다양한 방향으로 퍼지는지를 요약한다
3.3 Void Ratio
- VOID 신호가 포함된 반응의 비율
- 특정 지점에서
입력 회피나 응답 보류가 얼마나 자주 발생하는지를 나타낸다
3.4 Erosion
- 시간 경과에 따라
HIGH 또는 MID 반응의 밀도가 감소하는 양상
- 장기 상호작용에서
정렬 반응이 희석되거나 소실되는 경향을 관찰하는 데 사용된다
이 메트릭들은
“문제 여부”를 판단하기 위한 수단이 아니라,
입력 분포의 형태 변화를 기술하기 위한 요약값이다.

---
### 4. 시각화 레이어와의 분리
Strata는 시각화를 전제로 하지 않는다.
그래프, 파동, 지층, 히트맵 등의 표현은
Strata 메트릭을 소비하는 별도의 표현 레이어에서 구현된다.
이 분리는 다음을 보장한다.
- 엔진은 계산만 수행한다
- Strata는 집계만 수행한다
- 시각화는 해석을 강요하지 않는다
따라서 동일한 Strata 메트릭이라도,
게임, 연구 도구, 대시보드, 예술적 인터페이스 등
각 응용 시스템은 서로 다른 표현 방식을 선택할 수 있다.

---
### 5. 윤리적 경계와 사용 원칙
Strata 레이어는 집단 데이터를 다루기 때문에,
개별 사용자에 대한 해석이나 낙인으로 오용될 가능성을 가진다.
이를 방지하기 위해 다음 원칙이 적용된다.
- Strata 메트릭은 개별 사용자 피드백의 근거로 사용되지 않는다
- 집단 데이터는 익명화된 형태로만 취급된다
- Strata 결과는 설명적(descriptive) 정보로만 제공된다
Strata는
“사람이 어떤 존재인가”를 말하지 않는다.
다만 어떤 반응들이 어떻게 쌓였는가를 보여줄 뿐이다.

---
## VI. Usage Scenarios
본 장은 별이엔진이 어디에 “쓸 수 있는지”를 설명한다.
이는 특정 사용 방식을 권장하거나,
어디에 “써야 한다”고 주장하기 위한 것이 아니다.
별이엔진은 정서 반응을 구조화된 상태 정보로 제공하는 엔진이며,
아래 시나리오는 그 정보가
각기 다른 도메인에서 어떻게 참조될 수 있는지를 보여주는 예시에 불과하다.

---
### 1. Games & Interactive Fiction
게임과 인터랙티브 픽션에서
플레이어의 선택은 단발 이벤트가 아니라
반복되는 반응 패턴을 형성한다.
별이엔진은 플레이어가 보고한 감정, 이유, 선택 로그를 바탕으로
다음과 같은 상태 정보를 제공할 수 있다.
- 특정 캐릭터나 사건에 대한 정렬도 변화
- 반복 선택에서 나타나는 HIGH / MID / LOW / FIXATED 분포
- 반응 궤적 요약(bridge, contradiction 등)
게임 시스템은 이 정보를 이용해 다음과 같은 설계를 할 수 있다.
- 스토리 분기의 밀도 또는 깊이 조절
- 동일한 사건에 대해 다른 관점의 서사 제공
- 특정 선택 지점에서 설명 보강 또는 선택 축소
중요하게도,
별이엔진은 “플레이어가 무엇을 느껴야 하는지”를 제안하지 않는다.
엔진은 오직 반응 구조를 제공하며,
서사적 의미와 연출 전략은 전적으로 게임 시스템의 책임이다.

---
### 2. Therapy Support & Reflection Tools
상담 및 치료 환경에서
정서 반응의 변화는 중요한 관찰 대상이 될 수 있다.
그러나 별이엔진은 치료를 수행하지 않으며,
임상적 판단을 대체하지 않는다.
이 영역에서 별이엔진은
다음과 같은 보조적 도구로 활용될 수 있다.
- 내담자가 보고한 감정·이유·선택의 시간적 변화 기록
- 반복 상호작용에서 나타나는 반응 궤적의 시각적 요약
- 특정 주제나 질문에 대한 반응 분포의 비교
이러한 정보는
상담자나 전문가가
내담자의 반응을 다른 각도에서 관찰하기 위한 참고 자료로 사용될 수 있다.
별이엔진은
정서 상태를 해석하거나
개입 방향을 제시하지 않는다.
모든 임상적 판단과 개입의 책임은
전적으로 전문가에게 있다.

---
### 3. Education & Simulation Systems
교육 및 시뮬레이션 환경에서는
학습자의 인지적·정서적 반응이
문제 반복 속에서 변화하는 양상이 중요할 수 있다.
별이엔진은 다음과 같은 정보를 제공할 수 있다.
- 동일한 과제나 상황에 대한 정서 반응의 이동
- 반복 시도에서 나타나는 정렬도 분포 변화
- 특정 단계에서의 VOID 신호 증가 여부
교육 시스템은 이 정보를 바탕으로:
- 설명 방식의 조정
- 난이도 변화 시점 결정
- 학습 경로의 분기 설계
등을 참고 수준에서 설계할 수 있다.
이때 별이엔진의 출력은
학습자의 능력이나 태도를 평가하는 지표가 아니다.
엔진은 학습 반응이 어떻게 배열되고 변화했는지만을 제공한다.

---
### 4. Research & System Design Analysis
별이엔진은
특정 응용 도메인에 한정되지 않기 때문에,
연구 및 시스템 설계 분석 도구로도 활용될 수 있다.
예를 들어:
- 동일한 인터페이스 변화 전후의 반응 궤적 비교
- 특정 선택 구조가 반응 분산을 유도하는지 관찰
- 장면·질문·프롬프트 단위의 반응 밀도 분석(Strata 연계)
이러한 사용은
사람을 분석하거나 분류하기 위한 목적이 아니라,
시스템이 어떤 반응 구조를 만들어내는지를 점검하기 위한 것이다.

---
## VII. Limitations & Ethical Considerations
본 장은 별이엔진의 기능적 한계와 윤리적 경계를 명확히 하기 위한 것이다.
별이엔진은 정서 반응을 구조화하는 도구이며,
그 활용에는 분명한 제한과 책임 범위가 존재한다.

---
### 1. 표현상의 한계 (Expressive Limits)
별이엔진은
사용자가 보고한 감정·이유·선택 로그를 기반으로 작동한다.
따라서 엔진이 다루는 정서 반응은
보고된 입력의 범위에 한정된다.
- 비언어적 표현(표정, 억양, 신체 반응)은 포함되지 않는다.
- 보고되지 않은 감정이나 맥락은 계산 대상이 아니다.
- VAD 기반 표현은 정서의 모든 뉘앙스를 포착하지 못할 수 있다.
이러한 한계는 설계상의 결함이 아니라,
의도적으로 설정된 범위 제한이다.
별이엔진은 정서의 “완전한 재현”을 목표로 하지 않는다.

---
### 2. 해석과 책임의 분리
별이엔진이 제공하는 모든 출력은
설명적(descriptive) 상태 정보다.
엔진은 다음을 수행하지 않는다.
- 심리 상태에 대한 판정
- 행동에 대한 평가
- 바람직한 반응에 대한 제안
- 개입 또는 교정
정렬도, 버킷, 패턴 라벨은
관측된 반응 배열을 요약한 신호일 뿐이다.
그 의미를 어떻게 해석하고,
어떤 조치를 취할지는
항상 상위 애플리케이션 또는 인간 사용자의 책임이다.

---
### 3. 오용 가능성과 방지 원칙
별이엔진은 구조적으로 중립적인 도구이지만,
다음과 같은 방식으로 오용될 위험이 존재한다.

- 자동화된 의사결정의 단독 근거로 사용하는 경우

- 출력 필드에는 임상적 의미를 암시하는 명칭을 포함하지 않는다.
- 단일 점수로 사용자를 요약하지 않는다.
- 패턴 라벨은 상태가 아닌 관측 요약 신호로만 제공된다.

별이엔진은

## 정렬도 계산

### 1. 기본 계산 방식: 코사인 유사도 (Cosine Similarity)

현재 아카이브 기억 플레이에서 사용하는 정렬도 계산 방식입니다.

### 함수 위치
- 파일: `js/shared/math.js`
- 함수: `cosineSimilarity(vec1, vec2, anchorEmotions = null)`

### 계산 공식
```
cosineSimilarity = dotProduct / (magnitude1 * magnitude2)

where:
  dotProduct = Σ(vec1[key] * vec2[key]) for all keys
  magnitude1 = √(Σ(vec1[key]²))
  magnitude2 = √(Σ(vec2[key]²))
```

### 앵커 시스템
- **장면별 앵커가 있는 경우**: 해당 앵커만 사용
- **장면별 앵커가 없는 경우**: 기본 17개 앵커 사용

**기본 17개 앵커 (DEFAULT_EMOTION_ANCHORS)**:
- 부정/고통 (10개): `fear`, `sadness`, `anger`, `guilt`, `shame`, `isolation`, `numbness`, `moral_pain`, `helplessness`, `despair`
- 긍정/회복 (7개): `joy`, `hope`, `relief`, `gratitude`, `love`, `peace`, `comfort`

### 코드 구현
```javascript
export function cosineSimilarity(vec1, vec2, anchorEmotions = null) {
  if (!vec1 || !vec2) return 0;

  let keys;
  if (anchorEmotions && Array.isArray(anchorEmotions) && anchorEmotions.length > 0) {
    keys = anchorEmotions.map(anchor => normalizeAnchor(String(anchor)));
  } else {
    keys = DEFAULT_EMOTION_ANCHORS;
  }

  let dotProduct = 0;
  let mag1 = 0;
  let mag2 = 0;

  keys.forEach(key => {
    const v1 = vec1[key] || 0;
    const v2 = vec2[key] || 0;
    dotProduct += v1 * v2;
    mag1 += v1 * v1;
    mag2 += v2 * v2;
  });

  mag1 = Math.sqrt(mag1);
  mag2 = Math.sqrt(mag2);

  if (mag1 === 0 || mag2 === 0) return 0;
  return dotProduct / (mag1 * mag2);
}
```

### 결과 범위
- **0 ~ 1** 사이의 값
- 1에 가까울수록 두 감정 벡터가 유사함
- 0에 가까울수록 두 감정 벡터가 다름

---

### 2. 복합 정렬도 계산 (현재 미사용)

더 복잡한 정렬도 계산을 위한 함수가 존재하지만, 현재 아카이브 플레이에서는 사용되지 않습니다.

### 함수 위치
- 파일: `js/index.js`
- 함수: `calculateComplexAlignment(userVector, originalVector, anchorEmotions = null)`

### 계산 공식
```
totalAlignment = (emotionScore * 0.4) + (reasonScore * 0.4) + (voidScore * 0.2)

where:
  emotionScore = cosineSimilarity(userVector.base, originalVector.base)
  reasonScore = attributionMatch(0.5) + coreFearMatch(0.5)
  voidScore = 1.0 if both have same void status, else 0.0
```

### 구성 요소
### 1. **감정 유사도 (40%)**: 코사인 유사도로 계산
### 2. **이유 분석 일치도 (40%)**:
   - `attribution` 일치: 0.5점
   - `core_fear` 일치: 0.5점
### 3. **VOID 상태 일치도 (20%)**: 둘 다 VOID이거나 둘 다 아닌 경우 1.0점

### 2. 아카이브 파동 계산

### 함수 위치

- 함수: `computeArchiveWaveData(emotionVector, sceneTextLength, voidLevel)`

### 계산 방식
```javascript
function computeArchiveWaveData(emotionVector, sceneTextLength, voidLevel) {
  // 1. 감정 벡터 정규화
  const totalEmotion = Object.values(emotionVector).reduce((sum, val) => sum + (val || 0), 0);
  const normalizedEmotion = totalEmotion > 0
    ? Object.keys(emotionVector).reduce((acc, key) => {
        acc[key] = (emotionVector[key] || 0) / totalEmotion;
        return acc;
      }, {})
    : emotionVector;

  // 2. 강도 계산
  const intensity = Math.min(1, Math.max(0.3, totalEmotion / 8));

  // 3. 파동 포인트 생성
  const wavePoints = [];
  const width = Math.max(100, Math.min(500, sceneTextLength * 10));

  for (let i = 0; i < width; i++) {
    const x = i / width;
    const baseY = 0.5;
    const amplitude = voidLevel === 'high' ? 0.15 : 0.25;
    const frequency = 0.02 + intensity * 0.01;
    const y = baseY + Math.sin(x * Math.PI * 2 * frequency * 10) * amplitude;
    wavePoints.push({ x, y });
  }

  // 4. 지배적 감정에 따른 색상 결정
  const dominantEmotion = Object.keys(normalizedEmotion).reduce(
    (a, b) => normalizedEmotion[a] > normalizedEmotion[b] ? a : b,
    'fear'
  );

  const emotionColors = {
    fear: 'rgba(74,144,217,0.8)',
    sadness: 'rgba(90,122,154,0.8)',
    guilt: 'rgba(139,115,85,0.8)',
    anger: 'rgba(217,74,74,0.8)',
    longing: 'rgba(196,168,130,0.8)',
    isolation: 'rgba(74,74,90,0.8)',
    numbness: 'rgba(106,106,106,0.8)',
    shame: 'rgba(155,89,182,0.8)',
    moral_pain: 'rgba(155,89,182,0.8)'
  };

  return {
    wavePoints,
    color: emotionColors[dominantEmotion] || 'rgba(196,168,130,0.8)',
    intensity,
    voidLevel
  };
}
```

### 파라미터 설명

**1. Width (파동 너비)**
- 계산식: `Math.max(100, Math.min(500, sceneTextLength * 10))`
- 범위: 100 ~ 500
- 장면 텍스트 길이에 비례

**2. Amplitude (진폭)**
- VOID 레벨에 따라 결정:
  - `high`: 0.15
  - `low`: 0.25

**3. Frequency (주파수)**
- 계산식: `0.02 + intensity * 0.01`
- `intensity`: `Math.min(1, Math.max(0.3, totalEmotion / 8))`
- 전체 감정 강도에 비례

**4. Y 좌표 계산**
- 공식: `y = baseY + Math.sin(x * Math.PI * 2 * frequency * 10) * amplitude`
- `baseY`: 0.5 (중앙 기준선)

### 3. Admin 페이지 파동 계산

### 함수 위치
- 파일: `js/admin.js`
- 함수: `computeWaveData(emotionVector, sceneTextLength, voidLevel)`

### 계산 방식
```javascript
function computeWaveData(emotionVector, sceneTextLength, voidLevel) {
  const wavePoints = [];
  const freq = 0.02;

  for (let x = 0; x < sceneTextLength * 10; x++) {
    let y = 0;

    // 각 감정의 파동을 합산
    Object.entries(emotionVector).forEach(([emotion, value]) => {
      y += Math.sin(x * freq) * value * 50;
    });

    wavePoints.push({ x, y });
  }

  // VOID 레벨이 high면 진폭 감소
  if (voidLevel === 'high') {
    wavePoints.forEach(p => p.y *= 0.3);
  }

  // 색상 보간
  const avgColor = interpolateColors(emotionVector);

  return { wavePoints, color: avgColor };
}
```

### 차이점
- 라이브/아카이브와 달리 **각 감정의 파동을 합산**하는 방식 사용
- 색상은 **감정 벡터의 가중 평균**으로 계산

alignment >= 0.55 → HIGH
alignment < 0.35 → LOW
그 외 → MID
```

### 코드 구현
```javascript
export function getBucket(alignment, previousBucket = null, emotionHistory = null) {
  // FIXATED 체크
  if (emotionHistory && emotionHistory.length >= 3) {
    const last3 = emotionHistory.slice(-3);
    if (last3[0] === last3[1] && last3[1] === last3[2]) {
      return 'FIXATED';
    }
  }

  // 히스테리시스 적용
  if (previousBucket === 'HIGH' && alignment >= 0.45) return 'HIGH';
  if (previousBucket === 'LOW' && alignment <= 0.25) return 'LOW';

  // 첫 판정 또는 MID
  if (alignment >= 0.55) return 'HIGH';
  if (alignment < 0.35) return 'LOW';
  return 'MID';
}
```

### 버킷 상태
- **HIGH**: 정렬도 >= 0.55 (또는 이전 HIGH에서 >= 0.45)
- **MID**: 0.35 <= 정렬도 < 0.55
- **LOW**: 정렬도 < 0.35 (또는 이전 LOW에서 <= 0.25)
- **FIXATED**: 마지막 3회 감정이 모두 동일

# play-test 지도 핀 접근 규칙 (SSOT: `play-test.html`)

## 목적

`play-test.html`의 지도 화면은 **등고선 지형 + 핀(pin)** 으로 장면 접근 가능 범위를 표현한다.  
이 문서는 “어떤 핀이 클릭 가능해지는가(잠금/해제)”를 코드 기준으로 정리한다.

---

## 용어

- **core pin**: 일반 장면(기본 앵커 장면). `pin.type === 'core'`
- **bridge pin**: 잔여/중립 역할 장면. `pin.type === 'bridge'` (조건: `scene.scene_role === 'residual'`)
- **void pin**: void 장면(특정 조건에서만 열리는 특수 핀). `pin.type === 'voidPin'`
- **echo pin**: 최근 플레이(해석) 흔적 장식. `pin.type === 'echo'` (**항상 잠금**, 클릭 불가)

상태:

- `pin.state`: `'active' | 'locked'` (코드 내부 플래그)
- 렌더 클래스:
  - `active`: 클릭 가능(아직 방문 전인 경우)
  - `visited`: 이미 방문한 core/bridge/void
  - `locked`: 클릭 불가
  - `entrance`: “이번에 열려있는 새 입구” 강조

---

## 핀 배치 규칙 (좌표계)

### 1) core/bridge

- 원본 감정(`scene.original_emotion`)을 **AF 좌표**로 투영해 지도 좌표로 변환한다.
  - `emotionToMapCoords()` → `{ x, y }` in \([0,1]\)
  - 내부: `projectEmotionToAFContour()` 결과의 `x,z`를 `(HALF/SIZE)`로 정규화
- 핀이 완전히 겹치지 않도록 `mapCoordsSpread()`로 memory/scene 기반의 작은 오프셋을 더한다.

### 2) echo

- 최근 `plays`에서 `user_emotion`을 AF 투영 → 퍼센트 좌표(`vadToPercent`)로 찍고,
- 약간의 지터(jitter)를 더해 점군처럼 분포시킨다.
- **잠금 처리**(장식)라 클릭 경로에 영향 없음.

### 3) void

- void 장면이 존재하면 **고정 좌표**로 핀을 추가한다.
  - 현재: `x=88%`, `y=78%` (코드 상 고정)

---

## 접근(Unlock) 규칙 개요

접근 가능 목록은 `game.accessiblePinIds: Set<string>`로 관리한다.

핵심 흐름:

1. **초기 접근**: `applyInitialAccess()`
2. **플레이 후 접근 재계산**: `handleEmotionResult()` → `updateAccess(...)`
3. `syncPinStateFlags()` + `applyPinVisualFlags()`로 `active/locked/visited/entrance` 상태를 최종 반영

---

## 1) 초기 접근 규칙 (`applyInitialAccess`)

- 대상: `core + bridge` 핀만
- 아직 방문하지 않은(`!game.visitedCore[sceneId]`) 핀을 우선으로, 없다면 전체 코어 풀을 사용
- `sceneOrder` 오름차순으로 정렬 후 **최대 3개**를 열어준다
- void 장면이 존재하면 `voidPin`도 추가로 열어준다

즉, 시작하자마자 열리는 핀:

- **(core/bridge 중) 3개**
- **(+ void 장면이 있으면 voidPin 1개)**

---

## 2) 플레이 후 접근 규칙 (`updateAccess`)

### 입력

- `pattern`: 전이 패턴 (예: `echo_follow`, `bridge`, `contradiction`, `displacement`, `avoidance`, `fixation`)
- `emotionPosition`: 사용자 감정의 지도 좌표 `{x,y}` (AF 기반)
- `originSceneId`: 직전에 플레이한 core/bridge/void 장면 id

### 중심점(center) 계산

기본:

- `center = emotionPosition` (없으면 `{0.5, 0.5}`)

origin 보정:

- origin 핀이 존재하면 \(\text{center} = (center + originPin) / 2\) 로 평균

의도:

- “지금 감정 위치”와 “방금 방문한 장면 위치”를 절충해 다음 접근 범위를 결정

### 반경(rule.radius)

패턴별 반경(`TRANSITION_RULES`):

- `echo_follow`: 0.42
- `bridge`: 0.62
- `contradiction`: 0.36
- `displacement`: 0.48
- `avoidance`: 0.24
- `fixation`: 0.09

### 선택 알고리즘

대상은 항상 `core + bridge` 핀들(= `cores`).

1. **fixation + originPin 존재**: `selected = [originPin]`
2. 그 외:
   - \(d(center, pin) <= radius\) 인 핀을 1차 선택
   - 비었으면 \(radius * 1.85\) 로 확장해서 재시도
   - 그래도 비었으면 “아직 방문하지 않은 core/bridge 전부”
   - 그것도 비면 “core/bridge 전부”

### voidPin 추가 규칙

void 장면이 존재하고, 패턴이 아래 중 하나면 voidPin을 `selected`에 추가한다.

- `avoidance`
- `contradiction`

결과:

- `game.accessiblePinIds = new Set(selected.map(p => p.id))`

---

## 3) 잠금/활성/방문 플래그 (`syncPinStateFlags` + `applyPinVisualFlags`)

### `syncPinStateFlags()`

- core/bridge:
  - 방문했거나(`visitedCore`) 접근 Set에 포함이면 `active`, 아니면 `locked`
- voidPin:
  - 방문했거나 접근 Set에 포함이면 `active`, 아니면 `locked`
- echo:
  - 항상 `locked`

### `applyPinVisualFlags()`

렌더링용 플래그를 정리한다.

- echo:
  - 무조건 `locked` 처리, 나머지 플래그 리턴
- core/bridge/void:
  - `visited = visitedCore[sceneId]`
  - `canOpen = visited || accessiblePinIds.has(id)`
  - `locked = !canOpen`
  - `active = canOpen && !visited`
  - `entrance = canOpen && !visited`

즉, “이번에 열려있는 신규 핀”은 `entrance`로 애니메이션 강조된다.

---

## 클릭 동작 (`onPinClick`)

- `pin.locked` 이면 클릭 무시
- `core/bridge/voidPin` 모두 `enterSceneMode(pin)`로 진입
- `game.sealed` 상태면 전체 클릭 무시

---

## 디버깅 포인트

`updateAccess()` / `handleEmotionResult()`는 콘솔에 다음을 출력한다.

- center 좌표
- 패턴/반경
- 후보 핀 거리 분포
- 최종 선택된 accessible pin id 리스트

문제(핀 전부 잠김, 접근 범위 이상) 발생 시 이 로그가 1차 SSOT이다.

# 별이엔진 V4 — 궤적 기반 정렬도 (Trajectory-Based Alignment)

**버전:** V4 프로토타입 확정안  
**작성일:** 2026-03-27  
**작성자:** 박도한 (TEM / The Etched Mutation)  
**상태:** 구현 및 검증 대기

---

## 1. 별이엔진이 측정하는 것

별이엔진은 다음 질문에 답한다:

**A가 기억을 말했다. B가 그 기억을 읽고 반응했다. A와 B의 경험이 얼마나 비슷한가?**

이 "비슷함"을 0~1 사이의 숫자(alignment score)로 산출하는 것이 엔진의 유일한 역할이다. 엔진은 진단하지 않고, 해석하지 않고, 권고하지 않는다. 상태 정보만 제공한다.

---

## 2. 최종 공식

```
shape_raw = (scenes_played >= 3)
            ? cosine(flatten(delta_user), flatten(delta_original))
            : 1.0

shape     = max(0, shape_raw)
level     = mean(scene_scores)
void_mod  = (user_void && !original_void) ? 0.7 : 1.0

alignment = level × shape × void_mod
```

### 각 항목의 정의

**scene_score:** 한 장면에서 체험자의 감정 벡터와 기록자의 원본 감정 벡터 간 코사인 유사도. 범위 0~1.

**level_similarity (level):** 지금까지 방문한 모든 장면의 scene_score 평균. "장면마다 감정이 얼마나 비슷했는가"의 누적 지표.

**shape_similarity (shape):** 감정 변화량(delta)의 궤적을 비교한 코사인 유사도. "감정이 어떤 방향으로 움직였는가"가 비슷한가. 장면 3개 미만이면 1.0(= 형태 정보 없음, 수준만 반영). 음수는 0으로 클램프.

**void_modifier (void_mod):** 체험자가 감정 입력을 회피(VOID)했고 기록자는 드러냈을 때 ×0.7. 둘 다 VOID면 페널티 없음(1.0).

### delta 궤적 구성

체험자 B가 장면을 [3, 1, 4] 순서로 방문했다면:

```
B의 감정 궤적: [scene3_reaction, scene1_reaction, scene4_reaction]
A의 대응 궤적: [scene3_original, scene1_original, scene4_original]
  (= B의 방문 순서대로 A의 원본 감정을 재배열)

delta_B = [scene1_reaction - scene3_reaction, scene4_reaction - scene1_reaction]
delta_A = [scene1_original - scene3_original, scene4_original - scene1_original]

shape_raw = cosine(flatten(delta_B), flatten(delta_A))
```

### 디버그 출력

```json
{
  "alignment": 0.52,
  "level": 0.73,
  "shape_raw": 0.71,
  "shape": 0.71,
  "void_mod": 1.0,
  "shape_active": true,
  "scenes_played": 4,
  "formula": "L0.73 × S0.71 × V1.00 = 0.52"
}
```

---

## 3. 왜 이 공식이어야 했는가 — V1에서 V4까지의 경로

### V1: 코사인 유사도 단독

감정 벡터 간 코사인 유사도 하나로 정렬도를 산출. 단순하지만, "같은 감정이라도 이유가 다르면 다른 경험"이라는 TEM의 핵심 철학을 반영할 수 없었다.

### V2: 임베딩(0.65) + VAD(0.35)

텍스트 임베딩 코사인 유사도와 VAD 거리의 가중합. 임베딩이 감정과 이유를 분리하지 못하는 문제 — "엄마한테 미안해서 눈물이 났어"와 "친구한테 미안해서 눈물이 났어"가 임베딩 공간에서 매우 가까움. 이유를 구분하겠다는 목적에 부적합.

### V3: 감정(0.4) + 이유(0.4) + 태도(0.2)

이유를 직접 측정하기 위해 AI(Claude)가 자유 텍스트에서 attribution, core_fear, target 레이블을 추출. 세 가지 구조적 문제가 발견됨:

**문제 1 — 이유 축의 측정 도구가 불안정하다.** AI가 같은 텍스트에서 다른 레이블을 추출할 수 있고, 이 변동이 전체 정렬도에서 최대 0.14점(= 0.35 × 0.4) 차이를 만든다. 버킷 경계(HIGH ≥ 0.55, LOW < 0.35)를 고려하면 AI 노이즈만으로 버킷이 바뀔 수 있다.

**문제 2 — 이유 축의 해상도가 너무 낮다.** 이산 레이블 매칭은 약 15단계의 이산 집합에서만 값을 산출. 40%의 가중치를 가진 축이 연속적 유사도가 아니라 시나리오 분류에 가깝게 작동한다.

**문제 3 — 선형 결합이 축 간 보상을 허용한다.** 감정이 정반대(E=0)여도, 이유 레이블이 우연히 같으면(R=1), alignment가 0.54(= 0 + 0.4 + 0.14)로 HIGH 경계 직전까지 올라간다. "같은 감정이라도 이유가 다르면 다른 경험"이라는 철학의 역 — "다른 감정이라도 이유가 같으면 비슷한 경험" — 이 발생.

추가로 태도 축(20%)은 대부분의 경우 0.7로 고정되어 사실상 상수 오프셋으로 기능. 0.4/0.4/0.2 비율의 이론적·경험적 근거 부재.

### V4: 궤적 기반 정렬도

핵심 전환: **이유를 직접 측정하는 대신, 이유의 결과를 관찰한다.**

"같은 감정이지만 다른 이유"를 가진 두 사람은 다음 장면에서 다르게 반응한다. 장면 1에서 둘 다 슬픔을 느꼈더라도, "내 탓"이라고 느낀 사람은 장면 2에서 죄책감 쪽으로 이동하고, "그 사람 탓"이라고 느낀 사람은 분노 쪽으로 이동한다. 궤적이 갈라지면 이유가 달랐다는 것이 간접적으로 드러난다.

이로써:
- AI 레이블 추출 의존이 제거됨 (측정 도구 노이즈 제거)
- 연속적인 궤적 상관으로 해상도 제한 없음
- 곱셈 결합으로 축 간 보상 구조적 차단
- 근거 없는 가중치 비율 불필요
- 새로운 AI 호출 불필요, 코드가 오히려 줄어듦

---

## 4. 이론적 기반

### 4.1 정서 유사도 (Emotional Similarity)

별이엔진의 감정 축(level_similarity)의 이론적 토대.

정서 유사도는 같은 상황에서 다른 사람과 같은 감정을 경험하는 것을 말하며, 더 보람 있는 상호작용(Locke & Horowitz, 1990), 더 큰 공감(Preston & de Waal, 2002), 더 높은 대인 조율(Hatfield et al., 1994), 증가된 관계 만족도(Anderson et al., 2003; Gonzaga et al., 2007), 감소된 스트레스 반응(Townsend et al., 2014)과 연관된다.

별이엔진은 17차원 감정 앵커 벡터 간 코사인 유사도로 정서 유사도를 측정한다. VAD 공간 배치는 Warriner, Kuperman & Brysbaert(2013)의 13,915개 영단어 정서 규범 데이터에 기반한다.

- Warriner, A. B., Kuperman, V., & Brysbaert, M. (2013). Norms of valence, arousal, and dominance for 13,915 English lemmas. *Behavior Research Methods*, 45(4), 1191–1207.
- Bakker, I., & van der Voordt, T. (2014). The effect of the environment on affect, arousal and dominance: A re-examination. *Current Psychology*, 33(4), 414–441.

### 4.2 시간적 대인 정서 시스템 (Temporal Interpersonal Emotion Systems, TIES)

별이엔진 V4의 궤적 비교(shape_similarity)의 이론적 토대.

Butler(2011, 2017)는 감정을 개인 내부의 상태가 아니라, 시간에 걸쳐 전개되는 대인적 동적 시스템으로 개념화했다. TIES 프레임워크의 핵심 주장: 감정의 동적 패턴(dynamics)은 감정의 수준(level)과 독립적으로 관계의 질과 안녕(well-being)을 예측한다.

별이엔진 V4는 이 구분을 직접 구현한다: level_similarity가 수준을, shape_similarity가 동적 패턴을 각각 측정하며, 둘의 곱이 최종 정렬도가 된다.

- Butler, E. A. (2011). Temporal interpersonal emotion systems: The "TIES" that form relationships. *Personality and Social Psychology Review*, 15(4), 367–393.
- Butler, E. A. (2017). Emotions are temporal interpersonal systems. *Current Opinion in Psychology*, 17, 129–134.

### 4.3 정서 수렴 (Emotional Convergence)

궤적 비교가 "경험의 유사성"을 포착할 수 있다는 근거.

Anderson, Keltner & John(2003)은 연인 커플과 룸메이트가 1년에 걸쳐 정서 반응이 수렴한다는 것을 보여줬다. 이 수렴 자체가 관계 응집력과 관계 지속을 예측했다. 별이엔진의 shape_similarity는 이 정서 수렴의 순간적 스냅샷 — 두 사람의 감정 변화 방향이 같은 쪽으로 향하는지 — 을 측정한다.

- Anderson, C., Keltner, D., & John, O. P. (2003). Emotional convergence between people over time. *Journal of Personality and Social Psychology*, 84(5), 1054–1068.

### 4.4 인지적 평가 이론 (Cognitive Appraisal Theory)

V3의 이유 축이 참조했던 이론이자, V4가 그 측정 방식을 포기한 이유.

Lazarus & Folkman(1984)의 Transactional Model에 따르면, 같은 사건도 사람마다 다르게 평가(appraise)한다. Troiano et al.(2023)은 텍스트에 내포된 감정이 책임 소재(Agency), 통제 가능성(Control) 등의 평가 차원에서 구체화된다는 것을 보였다.

그러나 심리학에서 인지적 평가를 측정하는 검증된 도구(SAM, CAHS 등)는 전부 자기보고 척도(리커트)다. AI가 자유 텍스트에서 레이블을 추출하는 방식은 검증된 측정 도구가 아니며, 추출의 재현성(reproducibility)이 확인되지 않았다. V4는 인지적 평가를 직접 측정하는 대신, 평가 차이의 결과(= 궤적 분기)를 관찰하는 간접 접근으로 전환했다.

- Lazarus, R. S., & Folkman, S. (1984). *Stress, appraisal, and coping*. Springer.
- Troiano, E., et al. (2023). Dimensional modeling of emotions in text with appraisal theories. *Computational Linguistics*, 49(1).
- Peacock, E. J., & Wong, P. T. P. (1990). The Stress Appraisal Measure (SAM). *Stress Medicine*, 6(3), 227–236.

### 4.5 감정 궤적 그래프 (Emotional Trajectory Graphs)

궤적 간 유사도를 비교하는 방법론.

서사 분석에서 감정 궤적 그래프는 이미 확립된 방법론이다. 시간 순서로 정렬된 노드(장면)에 감정 속성(VAD 벡터, 범주 레이블 등)을 부여하고, 궤적 간 유사도를 스피어만 상관, SVD 분해, 코사인 유사도 등으로 비교한다.

별이엔진 V4의 shape_similarity는 이 방법론을 차용하되, 감정 값 자체가 아니라 감정 변화량(delta)의 궤적을 비교한다. 이로써 "감정의 절대적 수준"이 아니라 "감정이 어떤 방향으로 움직이는가"의 유사도를 측정한다.

- Reagan, A. J., et al. (2016). The emotional arcs of stories are dominated by six basic shapes. *EPJ Data Science*, 5(1), 31.
- Vishnubhotla, K., et al. (2024). Emotional arcs of narration and dialogue. *Computational Linguistics*.

### 4.6 기억유전학 (Mnemonic Genetics)

TEM 고유의 이론적 프레임워크. 별이엔진이 작동하는 맥락.

Park(2026)의 기억유전학은 유전학의 4연산(복제·변이·선택·번역)을 기억 동역학에 형식적으로 매핑하되, 기억은 "유전학적으로 불가능한" 연산(파괴적 복제, 편향적 변이, 의도적 선택, 무규칙 번역)이 실제로 작동한다고 주장한다.

궤적 비교는 이 프레임워크와 다음과 같이 정합한다:
- 파괴적 복제: 회상할 때마다 궤적이 달라진다 = 원본이 변형된 사본으로 덮인다
- 편향적 변이: delta의 방향이 현재 감정 상태에 의해 편향된다
- 의도적 선택: 어떤 장면을 먼저 방문할지가 궤적 형태를 결정한다

정렬도(alignment)는 유전학의 서열 상동성(sequence homology)과 구조적으로 대응하되, 물리적 서열 유사도가 아니라 두 의식의 감정 궤적이 수렴하는지(기능적 공명)를 측정한다.

- Park, D. (2026). Mnemonic Genetics: Four operations of memory dynamics. Working Paper v0.2.

---

## 5. 전이 패턴

alignment 점수와 별개로, 궤적의 형태에서 서사적 전이 패턴을 도출한다. 이 패턴은 점수 계산에 관여하지 않으며, 상위 애플리케이션(TEM)이 서사 분기와 시각적 연출에 사용한다.

| 패턴 | 판정 기준 | 의미 |
|---|---|---|
| echo_follow | 직전 2개 delta 방향 일치 | 감정이 잔향처럼 따라옴 |
| contradiction | 직전 delta 방향 반대 | 반대 방향으로 튕겨나감 |
| fixation | 직전 3개 감정 벡터 코사인 ≥ 0.85 | 같은 감정에 갇힘 |
| displacement | level 높고 shape 낮음 | 감정은 비슷했으나 궤적이 갈라짐 |
| avoidance | VOID 발생 | 감정 접근 회피 |
| bridge | 나머지 | 중립적 연결 |

displacement에 대한 주의: 이 패턴은 "같은 감정 + 다른 이유"의 확정이 아니라, "궤적 분기"의 감지다. 분기의 원인이 이유 차이인지 다른 요인(감정 추출 흔들림, 장면 텍스트 애매함, 타이밍 밀림 등)인지는 이 엔진으로 구분 불가하며, 서사 레이어에서도 단정하지 않고 관찰만 제시해야 한다.

## 8. 비선형 탐색 처리

TEM의 아카이브 플레이에서 체험자는 지도(등고선 지형 + 핀)에서 장면 방문 순서를 선택할 수 있다. A는 [1→2→3], B는 [3→1→4] 순서로 갈 수 있다.

궤적은 **체험자의 실제 방문 순서(시간적 흐름)**를 기준으로 구성한다. 서사적 고정 순서(장면 번호 순)가 아니다.

이유: TEM에서 어떤 장면을 먼저 열어봤는가는 이미 해석 행위다. 탐색 순서를 무시하고 장면 번호 순으로 재배열하면, 실제 플레이 경험을 버리고 "가상의 정렬된 독해"를 계산하게 된다.

원본(기록자 A)의 대응 궤적은, 체험자 B의 방문 순서에 맞춰 A의 원본 감정을 재배열하여 구성한다:

```
B가 [3, 1, 4] 순서로 방문:
  B의 궤적 = [B의 scene3 반응, B의 scene1 반응, B의 scene4 반응]
  A의 대응 = [A의 scene3 원본, A의 scene1 원본, A의 scene4 원본]
```

## 9. 설계 결정 기록

### 9.1 왜 곱셈 결합인가 (선형이 아니라)

V3의 `E×0.4 + R×0.4 + A×0.2`는 한 축이 0이어도 다른 축이 보상할 수 있었다. 감정이 정반대(E=0)여도 이유 레이블이 우연히 같으면(R=1) alignment가 0.54까지 올라감.

곱셈 결합 `level × shape`에서는 한 축이 0이면 전체가 0이 된다. 감정이 비슷해도 궤적이 반대면 정렬도가 낮고, 궤적이 비슷해도 감정이 다르면 정렬도가 낮다. TEM의 철학("같은 감정이라도 이유가 다르면 다른 경험")과 그 역("다른 감정이라도 이유가 같으면 같은 경험이 아님")을 모두 구조적으로 보장한다.

### 9.2 왜 shape의 음수를 0으로 클램프하는가

코사인 유사도는 -1~1 범위이므로, delta 궤적이 반대 방향이면 음수가 나온다. 음수를 허용하면 alignment가 음수가 되며, "반정렬(anti-alignment)"이라는 별도 개념이 필요해진다. 현재 단계에서는 이 개념이 정의되지 않았으므로, 반대 방향은 "매우 낮은 정렬도"(= 0)로 처리한다. contradiction 패턴이 이 상태를 서사적으로 포착한다.

프로토타입 검증 후 0이 과도하게 많이 나오면 `(1 + shape_raw) / 2`로 선형 변환하여 부드럽게 전환할 수 있다. 초기에는 효과를 강하게 관찰하기 위해 엄격한 클램프를 유지한다.

### 9.3 왜 장면 3개 미만에서 shape = 1.0인가

shape_similarity를 계산하려면 delta가 최소 2개 필요하고, delta 2개를 얻으려면 장면 3개가 필요하다. 장면이 부족할 때 shape를 1.0으로 놓으면 `alignment = level × 1.0 × void_mod = level × void_mod`가 되어, if/else 분기 없이 전 구간을 하나의 공식으로 커버한다.

이 설계에서 초반(1~2장면)의 alignment는 "형태 정보가 아직 없으므로 감정 수준만 반영한 잠정 값"이다. 디버그 출력의 `shape_active` 플래그가 이 상태를 명시한다.

### 9.4 왜 VOID를 축이 아니라 modifier로 강등했는가

V3의 attitude_score는 20%의 가중치를 가졌지만, 대부분의 플레이에서 양쪽 모두 비VOID이므로 0.7로 고정되어 사실상 상수 오프셋(0.14)으로 기능했다. 축이라기보다 바이어스였다.

V4에서는 VOID를 독립 축이 아니라 최종 alignment에 곱하는 보정치(modifier)로 변경했다. VOID가 발생했을 때만 작동하고, 발생하지 않았을 때는 alignment에 영향을 주지 않는다(×1.0).

### 9.5 왜 이유를 임베딩으로 대체하지 않았는가

검토했으나 기각. 사용자 텍스트에서 "이유 문장"을 추출하는 것 자체가 AI의 판단에 의존한다. 이산 레이블을 임베딩으로 바꿔도 분리 단계의 노이즈가 해결되지 않는다. 또한 감정 임베딩과 이유 임베딩을 분리하면 구조적으로 V2(통합 임베딩 단일 축)와 차이가 불명확해진다.

궤적 기반 접근은 이유를 측정하는 것 자체를 포기하고, 이유의 결과(= 다음 장면에서의 감정 변화 방향)를 관찰함으로써, AI 추출 의존성을 완전히 제거한다.

## 10. 검증 계획

### 10.1 1단계: 감정 벡터 추출 안정성 (1일)

텍스트 20개를 Claude에 5번씩 돌려 감정 벡터를 추출. 같은 텍스트에서 나온 5개 벡터의 쌍별 코사인 유사도 평균이 0.95 이상이면 안정적. 텍스트 유형(직접 서술 vs 은유적 서술)별 분산도 확인.

### 10.2 2단계: 기존 데이터 궤적 시뮬레이션 (1일)

plays 테이블의 기존 플레이 데이터로 delta를 구하고 shape_similarity 분포를 확인. 전부 0.9 이상이면 변별력 없음. 전부 0.1 이하면 노이즈. 0.3~0.8에 고르게 분포하면 작동.

### 10.3 3단계: 10명 파일럿 (1~2주)

10명에게 같은 기억을 플레이시킨 후 검증용 설문(플레이 후 별도 수집, 작품 UX와 무관):

1. "이 기억의 주인과 감정적으로 비슷하게 느꼈다" (1~7점) → level_similarity 대응
2. "이 기억의 흐름이 나와 닮았다" (1~7점) → shape_similarity 대응
3. "사건을 받아들이는 방식이 비슷했다" (1~7점) → 이유 축 부재 확인용 대조

trajectory_alignment와 자기보고 점수의 피어슨 상관 산출. 비교 기준: scene_score 평균 단독(= level만)과의 상관. trajectory_alignment가 유의미하게 높은 상관을 보이면 궤적 비교의 부가가치 입증.

### 10.4 실패 조건

3단계에서 trajectory_alignment와 자기보고 사이에 유의미한 상관이 없으면, shape를 버리고 `alignment = level × void_mod`(감정 유사도 단독)으로 간다. 이것이 가장 단순하고 가장 안정적인 베이스라인이며, 그 위에 다른 축을 추가할지는 데이터를 본 다음에 결정한다.

## 1. SceneNavigator

### 1.1 존재 이유

현재 main path의 씬 진행은 `currentScene + 1` (단순 선형)이다.
demo path는 하드코딩된 `SCENE_TRANSITION_MAP`으로 분기한다.

둘 다 문제가 있다:
- 선형: 엔진의 transition_pattern 출력을 완전히 무시
- 하드코딩: 특정 기억에만 적용 가능, 범용성 없음

SceneNavigator는 **감정 공간(VAD) 위의 실시간 반경 계산**으로 이 문제를 해결한다.
모든 기억에 범용 적용 가능하고, 엔진 출력이 직접 경로를 결정한다.

### 1.2 핵심 설계 결정: Pattern이 기하를 바꾼다

**위험한 설계 (기각됨):**
```
center = average(userEmotion, originalEmotion)  // 항상 같은 방식
radius = RADIUS_MAP[pattern]                     // pattern은 숫자 하나로 축소
```

이 구조에서 transition_pattern은 "반경 값 테이블"로 퇴화한다.
echo_follow(0.42)와 contradiction(0.36)의 차이가 단지 0.06 — 의미가 사라진다.

**채택된 설계:**
```
center = blend(originalEmotion, userEmotion, patternConfig[pattern])
radius = patternConfig[pattern].radius
candidates = rankByPattern(accessibleScenes, pattern, context)
```

center 자체가 pattern에 따라 이동하고, 후보 씬의 랭킹 로직도 pattern별로 다르다.

### 1.3 Pattern별 Center Shift + Radius

```javascript
const PATTERN_CONFIG = {
  echo_follow: {
    // 화자의 감정 쪽으로 가중 → 원본 근처에서 자연스럽게 이동
    blendWeight: { original: 0.7, user: 0.3 },
    radius: 0.42,
    rankBy: 'proximity_to_original'  // 원본 감정에 가까운 씬 우선
  },
  bridge: {
    // 균등 → 넓게 열린 중립 탐색
    blendWeight: { original: 0.5, user: 0.5 },
    radius: 0.62,
    rankBy: 'unvisited_first'  // 미방문 씬 우선
  },
  contradiction: {
    // 사용자 감정의 반대 방향 → 현재 감정과 먼 곳으로 튕김
    blendWeight: { original: 0.3, user: -0.5 },  // user를 반전 가중
    // 실제 계산: center = 0.3 * original + 0.5 * invert(user) + 0.2 * neutral
    radius: 0.36,
    rankBy: 'emotional_contrast'  // 현재 감정과 가장 다른 씬 우선
  },
  displacement: {
    // 감정 유지, 대상/귀인 축으로 이동
    blendWeight: { original: 0.4, user: 0.6 },
    radius: 0.48,
    rankBy: 'attribution_shift'  // 같은 감정이지만 다른 attribution을 가진 씬 우선
  },
  avoidance: {
    // void/neutral 영역으로 밀림
    blendWeight: { original: 0.2, user: 0.2, neutral: 0.6 },
    radius: 0.24,
    rankBy: 'low_intensity'  // 감정 강도가 낮은 씬 우선
  },
  fixation: {
    // 현재 씬 좌표에 거의 고정
    blendWeight: { original: 0.1, user: 0.0, current: 0.9 },
    radius: 0.09,
    rankBy: 'nearest'  // 가장 가까운 것만
  }
};
```

### 1.4 Center 계산 수식

```javascript
function calculateCenter(originalEmotion, userEmotion, currentSceneEmotion, pattern) {
  const config = PATTERN_CONFIG[pattern];
  const w = config.blendWeight;

  if (pattern === 'contradiction') {
    // 사용자 감정을 VAD 공간에서 반전
    const invertedUser = invertVAD(userEmotion);
    return blendVectors([
      { vec: originalEmotion, weight: w.original },
      { vec: invertedUser, weight: Math.abs(w.user) },
      { vec: NEUTRAL_POINT, weight: 1 - w.original - Math.abs(w.user) }
    ]);
  }

  if (pattern === 'avoidance') {
    return blendVectors([
      { vec: originalEmotion, weight: w.original },
      { vec: userEmotion, weight: w.user },
      { vec: NEUTRAL_POINT, weight: w.neutral }
    ]);
  }

  if (pattern === 'fixation') {
    return blendVectors([
      { vec: originalEmotion, weight: w.original },
      { vec: currentSceneEmotion, weight: w.current }
    ]);
  }

  // echo_follow, bridge, displacement
  return blendVectors([
    { vec: originalEmotion, weight: w.original },
    { vec: userEmotion, weight: w.user }
  ]);
}
```

### 1.5 접근 가능 씬 결정

```javascript
function getAccessibleScenes(scenes, center, radius, visitedScenes, pattern) {
  const config = PATTERN_CONFIG[pattern];

  // 1. 반경 내 씬 필터
  let candidates = scenes.filter(s =>
    vadDistance(s.original_emotion, center) <= radius
    && s.id !== currentSceneId
  );

  // 2. pattern별 랭킹
  candidates = rankCandidates(candidates, config.rankBy, {
    originalEmotion: currentScene.original_emotion,
    userEmotion: currentUserEmotion,
    visitedScenes
  });

  // 3. 최소 1개 보장 (폴백)
  if (candidates.length === 0) {
    candidates = [getNearestUnvisited(scenes, center, visitedScenes)];
    candidates[0]._isFallback = true;  // 내러티브 프레이밍 트리거
  }

  return candidates;
}
```

### 1.6 폴백 규칙

accessible이 0개일 때 가장 가까운 미방문 씬을 강제 개방하되, **조용히 열지 않는다.**

프론트엔드는 `_isFallback === true`를 감지하면 내러티브 메시지를 표시:
- "기억의 빈틈이 다른 장면을 끌어당긴다."
- "가장 가까운 잔향이 떠오른다."
- "어딘가에서 소리가 들린다."

이 메시지는 규칙 위반이 아니라 기억 시스템의 보정처럼 체감되어야 한다.

### 1.7 씬 ≤ 3개: B 폴백

씬이 3개 이하인 기억에서는 반경 계산이 의미를 잃는다 (거의 모든 씬이 반경 안에 들어감).

이 경우:
- 반경 계산 대신 **감정 거리 순 정렬**로 전체 개방
- 단, 방문 순서에 따라 delta 궤적은 여전히 추적
- pattern은 여전히 AI/오염 피드에 사용

### 1.8 Fixation 감지: 복합 신호

**단순 count 기반 (기각됨):**
```
fixationCounts[sceneId] >= 2 → FIXATED  // 너무 기계적, 부당할 수 있음
```

**채택: pattern persistence 기반:**
```javascript
function detectFixation(context) {
  const {
    recentEmotions,      // 최근 3회 감정 벡터
    recentAttributions,  // 최근 3회 attribution
    accessibleCount,     // 접근 가능했던 씬 수
    actualMoves,         // 실제 이동한 씬 수 (다른 씬으로)
    fixationCounts       // 보조: 같은 씬 방문 횟수
  } = context;

  let score = 0;

  // 1. 최근 감정 유사도 (주 신호)
  if (recentEmotions.length >= 3) {
    const pairwiseSim = avgPairwiseCosineSim(recentEmotions);
    if (pairwiseSim > 0.85) score += 0.4;
    else if (pairwiseSim > 0.7) score += 0.2;
  }

  // 2. attribution 반복 (보조 신호)
  if (recentAttributions.length >= 2) {
    const allSame = recentAttributions.every(a => a === recentAttributions[0]);
    if (allSame) score += 0.2;
  }

  // 3. 탐색 회피율 (보조 신호)
  if (accessibleCount > 1 && actualMoves > 0) {
    const explorationRatio = new Set(actualMoves).size / accessibleCount;
    if (explorationRatio < 0.3) score += 0.2;
  }

  // 4. 동일 씬 재방문 (보조 가중)
  const maxRevisit = Math.max(...Object.values(fixationCounts));
  if (maxRevisit >= 2) score += 0.15;
  if (maxRevisit >= 3) score += 0.15;

  return {
    isFixated: score >= 0.6,
    score,
    // 갇힘 엔딩 트리거: fixation 점수 높고 + 충분한 방문 횟수
    forceEnding: score >= 0.8 && Object.values(fixationCounts).reduce((a, b) => a + b, 0) >= 5
  };
}
```

fixation은 "패턴의 지속"이지, "숫자의 도달"이 아니다.

### 1.9 종료 조건

| 조건 | 결과 |
|------|------|
| 모든 씬 방문 완료 | 정상 엔딩 |
| fixation.forceEnding === true | 갇힘 엔딩 |
| 엔딩 타입 씬(sceneType === 'ending') 도달 | 해당 엔딩 |
| 방문 횟수 >= 씬 수 × 2 | 안전장치 엔딩 (무한루프 방지) |

### 1.10 플레이어 UI: 안개 속 국소 구조

**하지 않는 것:**
- 전체 감정 공간 맵 노출
- 모든 씬 위치 표시
- 반경 원 시각화
- 접근 불가 씬의 흐린 표시

**하는 것:**
- 현재 위치에서 접근 가능한 씬들만 "떠오르는 문장 조각"으로 등장
- 각 조각은 감정 색조(emotion → RGB 매핑)를 띰
- 거리감은 문장의 선명도/크기로 표현 (가까울수록 또렷)
- 선택 시 자연스러운 전환 (fog transition)
- 폴백 씬은 특별한 시각 처리 (잔향 효과)

"우주 지도"가 아니라 "안개 속에서 가까운 장면들이 떠오르는 감각"

## 4. Record 통합: 기억을 말하는 행위가 첫 번째 Play

### 4.1 핵심 명제

> 기억을 말하는 행위 자체가 이미 첫 번째 Play다.

Record는 데이터 수집 UI가 아니라 기억 변이의 최초 사건이다.
화자는 자기 기억의 첫 번째 경험자이고, 말하는 과정에서 이미 파괴적 복제가 시작된다.

### 4.2 Pattern-Aware AI Questioning

Record 대화 중 AI("또 다른 나")의 질문 방향을 감지된 pattern으로 조절.

**원칙: AI는 pattern을 명명하지 않는다. 질문의 결만 바꾼다.**

| 감지 pattern | AI 질문 리듬 | 하지 않는 것 |
|---|---|---|
| echo_follow | 짧고 전진. "그래서 그 다음엔?" "또?" | "자연스럽게 흘러가고 있네요" (해석) |
| contradiction | 전환 확인, 중립. "다른 장면인 것 같아." | "아까랑 완전 다른 감정이네요" (진단) |
| avoidance | 침묵/간격/선택형. "..." 또는 "[말해도 되고, 넘어가도 돼]" | "회피하고 있는 것 같아요" (지적) |
| fixation | 감각/장소/신체로 초점 이동. "그때 어디에 있었어? 뭐가 보였어?" | "계속 같은 이야기를 하고 있어" (판단) |
| bridge | 열린 질문. "그때 어떤 느낌이었어?" | (특별한 제약 없음) |
| displacement | 대상 전환 유도. "그 사람은 어땠을까?" | "감정은 같은데 대상이 다르네요" (분석) |

**구현 위치:** `collect-memory` Edge Function의 system prompt에 현재 감지 pattern을 주입.
프론트엔드(`recordChat.js`)에서 축적된 감정 벡터로 pseudo-pattern을 추출하고 API 호출 시 전달.

### 4.3 Pseudo-Pattern 추출 (Record용)

Record에서는 별이엔진을 직접 돌리지 않는다 (비교 대상인 "원본"이 아직 없으므로).
대신, 화자의 감정 궤적 자체에서 패턴을 추출한다:

```javascript
function extractRecordPattern(emotionHistory) {
  if (emotionHistory.length < 2) return 'bridge';  // 초기: 열린 질문

  const recent = emotionHistory.slice(-2);
  const delta = subtractVAD(recent[1], recent[0]);
  const magnitude = vadMagnitude(delta);
  const similarity = cosineSimilarity(recent[0], recent[1]);

  // 감정 변화 없음 → fixation 후보
  if (similarity > 0.9 && magnitude < 0.1) {
    return emotionHistory.length >= 3 ? 'fixation' : 'echo_follow';
  }

  // 큰 반전 → contradiction
  if (similarity < 0.2 || magnitude > 0.6) return 'contradiction';

  // void 입력 → avoidance
  if (recent[1]._isVoid) return 'avoidance';

  // 감정 유사 + 다른 대상 → displacement
  if (similarity > 0.7 && recent[1].attribution !== recent[0].attribution) {
    return 'displacement';
  }

  // 자연스러운 흐름 → echo_follow
  if (similarity > 0.6) return 'echo_follow';

  return 'bridge';
}
```

### 4.5 명명 규칙

| 기존 용어 | 교정 | 이유 |
|----------|------|------|
| original emotion | initial telling emotion | "원본"은 TEM의 철학에 위배 |
| original trajectory | telling trajectory (최초 진술 궤적) | 순수 원본을 전제하지 않음 |
| narrator's original | narrator's telling | 말해진 것이지, 있었던 것이 아님 |

새로운 필드는 `telling_trajectory`로 명명.

- "지금까지의 기억 지형 보기" 버튼

# PLAY 진입 재설계 — 설계 결정 문서 v1

**작성일:** 2026-03-30
**상태:** 설계 확정, 구현 보류 (contamination 체감 + Record 통합 + 지형 시각화 완료 후)
**예상 작업 시점:** 제출 3~4주 전

---

## 핵심 전환

### 기존

> "기억은 보관된 것이고, 사용자가 찾아간다."

ARCHIVE = 보관소. 목록 → 선택 → 체험. 메뉴 탐색에 가깝다.

### 변경안

> "기억은 이미 살아 있고, 사용자의 상태에 반응해 먼저 모습을 드러낸다."

PLAY = 기억 탐색 엔진. 해석이 선택보다 먼저 시작된다.

---

## 구조

### 현재 흐름

```
PLAY/ARCHIVE 클릭
  └→ 기억 목록 (카드형, 제목/코드/레이어 수 표시)
       └→ 기억 선택
            └→ 장면 시작
```

### 변경 후 흐름

```
PLAY 클릭
  └→ "무슨 기억을 찾으러 왔어?" (또 다른 나)
       └→ 사용자 응답 (자유 텍스트 or 감정 칩, 1~2턴)
            └→ 감정 벡터 추출
                 └→ 기억 DB에서 코사인 유사도로 3개 선택
                      └→ 혼잣말 3개 화면에 표시
                           └→ 사용자가 하나 선택
                                └→ "네가 방금 고른 말 때문에 이 기억이 반응했다." (한 줄)
                                     └→ 장면 시작
```

**동시에 화면 어딘가에 희미하게:**
→ "직접 아카이브를 둘러보기" (작은 입구, 자유 탐색 보존)

---

## 혼잣말 3개 설계 원칙

### 소스

AI 새 생성 **아님**. DB 안에 이미 존재하는 텍스트에서 꺼낸다:
- `memories.completed_sentence` — 기억의 핵심 문장 (가장 우선)
- `scenes.scene_text` 일부
- `scenes.echo_words`
- 과거 플레이어 파편 (향후)

**이유:** "AI가 만든 추천 문장"이 아니라 "기억들이 너를 향해 먼저 말을 건다"는 감각이어야 한다. 재배열과 조우. 생성이 아니다.

### 3개 구성 방식

동일한 감정 좌표 3개를 주면 안 된다. 의도적으로 편차를 만든다:

| 순서 | 특성 | 역할 |
|------|------|------|
| 첫 번째 | 사용자 벡터와 가장 가깝다 | 공명 — "이건 내 얘기 같은데?" |
| 두 번째 | 비슷하지만 결이 다르다 | 변주 — 유사하지만 낯선 각도 |
| 세 번째 | 뜻밖이지만 기묘하게 끌린다 | 이탈 — 예상 밖의 당김 |

세 번째가 없으면 추천 엔진이 된다. 세 번째가 있어야 탐색이 된다.



---

## 성공 조건 (세 가지)

1. **자유 탐색을 완전히 없애지 말 것.**
   시스템이 너무 큐레이션 중심이 되면 "기억의 미로"가 "추천 엔진"으로 느껴진다. 자유 아카이브 입구는 작지만 남긴다.

3. **혼잣말은 정보가 아니라 정서적 bait여야 한다.**
   설명문이 되면 망한다. 분석 결과를 말하지 말고, 분석이 응축된 문장을 보여줘야 한다.

   ❌ "당신이 찾는 기억은 상실과 죄책감이 섞인 기억입니다."
   ✅ "그때 나는 대체 왜 아무 말도 못 했을까."
   ✅ "돌아가고 싶었던 건 그 사람이 아니라 그때의 나였는지도 몰라."
   ✅ "아무 일도 없었다고 믿고 싶은 기억이 있다."

---

## 위험 지점 목록

| 위험 | 증상 | 대처 |
|------|------|------|
| 자유 탐색 제거 | 사용자 통제권 소멸, 추천 엔진처럼 보임 | 자유 아카이브 입구 유지 |
| 대화가 길어짐 | 검색창 UX가 됨, 리듬 사망 | 1~2턴 하드컷 |
| 혼잣말이 설명문이 됨 | 분석 결과를 직접 노출, 몰입 파괴 | 정서 문장만, 이유 절대 설명 안 함 |
| 3개가 너무 맞춤형 | 미스터리 사라짐, 세계 좁아짐 | 의도적 편차 — 세 번째는 뜻밖 |
| 선택 후 연결 설명 없음 | 랜덤 추천처럼 보임 | 한 줄 브리지: "이 기억이 반응했다" |
| 선택 후 설명 과잉 | 구림 | 한 줄 이상 금지 |
| 재플레이 유저 마찰 | 매번 대화 타야 해서 귀찮음 | 자유 탐색 입구로 우회 가능하게 |

## 구현 시 기술 선택지

**"무슨 기억을 찾으러 왔어?"에 대한 응답 처리:**

| 방식 | 특성 | 판단 |
|------|------|------|
| 감정 칩 선택 (expInterview 재사용) | 구현 쉬움, 대화 느낌 약함 | fallback |

| 자유 텍스트 → quickAnalyze (키워드) → 근사 벡터 | 무료, 정밀도 낮음 | 저예산 대안 |

**기억 매칭 알고리즘:**
기존 SceneNavigator와 동일한 코사인 유사도. 단, 장면 단위가 아니라 기억 단위로 집계. `memories` 테이블의 `original_emotion`이 없다면 해당 기억의 장면 벡터 평균을 사용.

**선택 자체가 데이터:**
어떤 혼잣말을 골랐는지를 `baseline_emotion`으로 기록. 플레이 시작 전 감정 좌표가 생겨 정렬도 계산의 reference point가 된다. 현재 구조에는 이게 없다.

# Record Flow V3: 무대 — 공명 — 침전

> 작성: 2026-04-04
> 해결 대상: Feedback #22, #26, #27, #29
> 상태: 설계 확정, 구현 전

---

## 배경: 왜 V3가 필요한가

V2(Confession Flow)의 문제:
- **#22** 유도 질문이 맥락 없이 반복 ("더 말해줘" 앵무새)
- **#26** 사용자가 행동만 나열 ("~하고, ~하고, ~했다")
- **#27** 장면을 "만든다"는 경험이 없음 (질문 → 응답 → 추출, 사용자는 수동)
- **#29** 감정 고저차 없는 기억은 궤적이 빈약 → 기록 자체가 메마름

V2 구조의 근본 한계: 의식 5단계 → AI 대화 → 장면 일괄 추출. 사용자에게 "장면이 생기는 과정"이 보이지 않고, AI 질문에 구조적 근거가 없음.

--

## 설계 원칙

1. **감각이 먼저, 서사는 나중.** 사용자가 "그 장소에 서 있는 상태"에서 말하게 한다.
2. **구성요소가 채워지는 것이 보인다.** 대화 중 시각/청각 요소가 실시간 반응.
3. **Phase 경계가 사용자에게 보이지 않는다.** A→B 전환이 자연스러운 대화 흐름.
4. **앵커 이미지는 기존 `anchor_images` 시스템을 사용한다.** 키워드 매칭 시 DB에 등록된 앵커가 있으면 image_type(text/ascii/photo)과 vividness 범위에 따라 표시. 없으면 텍스트 앵커로 폴백. Record 중에는 기억이 아직 형성 중이므로 vividness를 낮게(0~0.4) 적용 — ascii/text 우선, photo는 억제.
5. **침묵과 부재도 기록된다.** VOID 선택은 빈 공간으로 남고, 그것도 지층의 일부.

---

## Phase A: 무대 (Staging) — 60~90초

### 진입

```
[화면: 검은 안개. 아무것도 없음.]

시스템 텍스트 (타이핑): "눈을 감아봐. 그 장소에 서 있어."
```

### 감각 칩 3종 — 순차 제시

각 칩 선택 후 즉시 감각 피드백. 다음 칩은 이전 선택에 반응하는 문장으로 연결.

**냄새:**
```
"무슨 냄새가 나?"

[ Metallic rain ] [ Acrid dust ] [ Antiseptic ] [ Fresh grass ] [ Nothing ]

→ 선택 시: 배경 색조 틴트 변화
  - rain_heavy: 짙은 청회색 (습기)
  - dust: 탁한 황갈색 (건조)
  - hospital: 차가운 백색 (무균)
  - grass: 옅은 녹색 (자연)
  - nothing: 색조 변화 없음 (어둠 유지)
```

**소리:**
```
[nothing이 아닌 경우] "그 냄새 사이로, 무슨 소리가 들려?"
[nothing인 경우]      "냄새는 없어. 대신 무슨 소리가 들려?"

[ Rainfall ] [ Silence ] [ Murmuring ] [ Wind ] [ Nothing ]

→ 선택 시: 앰비언스 사운드 레이어 시작
  - rain: 빗소리 루프
  - silence: 극저주파 앰비언스 (완전한 무음이 아닌, "적막")
  - crowd: 웅성거림 루프
  - wind: 바람 루프
  - nothing: 앰비언스 없음
```

**촉감:**
```
"피부에 닿는 건?"

[ Cold air ] [ Clammy sweat ] [ Someone's hand ] [ Hard floor ] [ Nothing ]

→ 선택 시: 화면 질감 변화
  - cold_air: 미세한 노이즈 레이어 (서리 입자)
  - sweat: 화면 약간의 습기감 (가장자리 블러 미세 변화)
  - someones_hand: 따뜻한 가장자리 빛 (미미한 비네팅 완화)
  - hard_floor: 하단 노이즈 레이어 (딱딱한 질감)
  - nothing: 변화 없음
```

### 앵커 오브젝트

```
시스템: "그 공간에서 눈이 머무는 것이 있어. 뭐야?"

→ 자유 텍스트 입력
→ 입력된 텍스트가 안개 속 앵커로 떠오름 (흐릿하게, opacity ~0.3)
```

### Phase B 전환 (사용자에게 보이지 않음)

→ 입력 UI가 자연스럽게 대화 모드로 전환
→ 이후 사용자 입력은 AI 대화로 처리
```

## Phase B: 공명 (Resonance) — 3~7턴

### 화면 상태

Phase A에서 세팅된 감각 무대 위에서 대화 진행:
- 배경 색조 (Phase A 냄새)
- 앰비언스 사운드 (Phase A 소리)
- 질감 레이어 (Phase A 촉감)
- 앵커 오브젝트 텍스트 (흐릿하게 떠다님)
- Another Me 파형 (기존 ghost wave)

### 구성요소 실시간 감지 — 이중 레이어 아키텍처

핵심 문제: Edge Function(Claude API)은 1~3초 걸린다. 그 사이 화면이 멈추면 "말하는 대로 장면이 나타남" 경험이 깨진다. 그러나 클라이언트 사이드 키워드 매칭만으로는 "울어버렸어"가 감정인지, "엄마가 울어버렸어"에서 인물+감정인지 구분 안 된다.

**해결: 이중 레이어. 즉시 반응 + 비동기 보정.**

**구성요소 5종:**

| 요소 | 감지 기준 | 시각/청각 반응 |
|------|----------|--------------|
| 장소/배경 | 공간을 나타내는 명사/구 | 배경 색조 심화 (Phase A 틴트 위에 더 구체적 톤 겹침) |
| 인물 | 사람을 지칭하는 명사/대명사 | 두 번째 파형 등장 (타인의 존재 암시) |
| 사물 | 구체적 사물 명사 | 텍스트 앵커 추가 부상 (안개 속에서) |
| 감정 | 감정어, 감정 표현 | 감정 파동 색/진폭 변화 |
| 신체감각 | 신체 반응 표현 | 화면 미세 진동 또는 노이즈 변화 |

#### Layer 1: 클라이언트 즉시 반응 (0ms)

사용자가 입력을 제출하는 순간, 클라이언트에서 사전 기반 패턴 매칭. 정밀할 필요 없다 — "뭔가 감지됐다"는 시각 신호만 주면 된다.

```javascript
const PATTERNS = {
  place:     /집|방|학교|거리|병원|문구점|화장실|부엌|교실|놀이터|room|school|street|hospital|home/,
  person:    /엄마|아빠|친구|선생|그\s?사람|누나|형|동생|할머니|mom|dad|friend|teacher/,
  object:    /칼|컵|사진|편지|핸드폰|가방|의자|거울|knife|cup|photo|letter|phone/,
  emotion:   /울|화|무서|슬|기쁘|짜증|부끄|미안|겁|cry|angry|scared|happy|sad/,
  sensation: /떨|차가|뜨거|아프|숨|심장|땀|어지러|shiver|cold|hot|pain|heart|sweat/
};
```

**복합어 오매칭 방지:**

```javascript
// "칼바람"의 "칼"처럼 더 큰 단어의 일부인지 체크
function isCompoundPart(text, matchWord, matchIndex) {
  const before = text[matchIndex - 1];
  const after = text[matchIndex + matchWord.length];
  if (before && /[가-힣a-z]/i.test(before)) return true;
  if (after && /[가-힣a-z]/i.test(after)) return true;
  return false;
}
// 복합어 일부이면 Layer 1에서 스킵 → Layer 2에만 맡김
```

매칭 시 → 해당 요소가 opacity 0.15로 흐릿하게 떠오름 ("감지 중" 예고 상태).

#### Layer 2: Edge Function 비동기 보정 (1~3초 후)

`extract-scene-elements` Edge Function 호출. 응답 도착 시 Layer 1 결과와 대조:

| 상태 | Layer 1 | Layer 2 | 처리 |
|------|---------|---------|------|
| **confirm** | 매칭 O | 일치 | opacity 0.15 → clarity 값(0.4)으로 fade-in. 자연스러운 "선명해짐" |
| **correct** | 매칭 O | 다른 요소 | 잘못된 요소 fade-out (0.5초) + 올바른 요소 fade-in. 안개가 형태를 잡아가는 과정 |
| **add** | 매칭 X | 감지됨 | 새 요소가 1~2초 뒤 안개 속에서 떠오름. "기억이 천천히 떠오르는" 느낌 |
| **none** | 매칭 X | 감지 X | 시각 변화 없음 |

**레이턴시가 미학이 된다:** correct/add 전환이 "안개 속에서 형태를 잡아가는" TEM의 시각 언어와 일치.

---

#### Edge Function 호출 전략 — 조건부 호출

매 턴 호출하지 않는다. 조건부:

| 조건 | 호출 여부 | 이유 |
|------|----------|------|
| Layer 1 매칭 없음 | **즉시 호출** | 간접 표현("뭔가 잘못됐다는 걸 알았어")이 감정일 수 있음 |
| Layer 1 확실한 매칭 (완전 단어, 복합어 아님) | **이 턴 스킵 가능** | 즉시 반응으로 충분 |
| Layer 1 애매한 매칭 (부분 매칭, 복합어 가능성) | **즉시 호출** | 오매칭 보정 필요 |
| clarity >= 0.7 요소가 2개 이상 (장면 전환 임박) | **매 턴 호출** | 장면 완성 판정의 정밀도 필요 |

평균 호출 빈도: 매 턴 → ~1.5턴당 1회. API 비용 약 40% 절감.

---

#### Edge Function 설계

```javascript
// extract-scene-elements — Haiku로 경량 처리
{
  model: "claude-haiku-4-5-20251001",  // Sonnet 아니다. 분류 작업이니 Haiku로 충분.
  max_tokens: 200,
  system: `Extract scene elements from user text. Return JSON only.
Types: place, person, object, emotion, sensation.
Resolve pronouns to existing elements when possible.
Currently detected elements: ${JSON.stringify(currentElements)}
Return: [{"type":"...","label":"...","confidence":0.0-1.0}]
If a pronoun (그 사람, 걔, etc.) refers to an existing element, return that element's label.
Empty array if none found. No explanation.`,
  messages: [
    { role: "user", content: last3Turns.join('\n---\n') + '\n---\n' + currentInput }
  ]
}
```

핵심: **최근 3턴 + 현재 요소 목록**을 같이 보낸다. 대명사/지시어 해소(coreference)를 위해.
- "엄마가 거기 있었어" → person: 엄마
- "그 사람이 소리를 질렀어" → 기존 "엄마" 요소의 clarity +0.2 (새 앵커 안 뜸)
- "걔가 울었어" → 기존 "엄마" 요소 참조 + emotion: 울다 추가

Haiku 응답: 300~800ms. Phase B의 "Another Me" 대화(Sonnet)와 별도 병렬 호출.

#### 전체 처리 흐름

```
사용자 입력 제출
  ├─ [즉시] Layer 1: 클라이언트 패턴 매칭
  │     → 매칭 시 예고 시각 효과 (opacity 0.15)
  │     → 복합어이면 스킵
  │
  ├─ [즉시] "Another Me" AI 응답 생성 (Sonnet, streaming)
  │     → 대화는 즉시 진행, 레이턴시 없음
  │
  └─ [비동기, 조건부] Layer 2: extract-scene-elements (Haiku)
        → 응답 도착 시 Layer 1 결과를 confirm/correct/add/none
        → clarity 값 업데이트
        → 시각 요소 fade-in/out 전환
```

사용자 체감: 말하면 즉시 뭔가 반응하고, AI가 답하는 동안 장면이 서서히 형태를 잡는다.

### 선명도 시스템

각 구성요소는 `clarity: 0 ~ 1` 값을 가짐.

```
Layer 1 예고 등장:  0.15 (흐릿한 실루엣)
Layer 2 confirm:   → 0.4 (첫 언급 확정)
감각 심화 답변:     +0.3
반복 언급/재참조:   +0.2
```

시각적으로: clarity 0은 안개 속(invisible), 1은 선명(fully visible).
중간값은 opacity, blur 보간으로 표현.

```javascript
elementState = {
  type: 'place' | 'person' | 'object' | 'emotion' | 'sensation',
  label: string,           // 원문 텍스트 (대명사 해소된 라벨)
  clarity: 0.0 ~ 1.0,
  visualRef: string | null, // 연결된 시각 요소 ID
  source: 'layer1' | 'layer2' | 'confirmed'  // 현재 상태
}
```

### 장면 전환 조건

**N개(기본값 3) 요소가 clarity >= 0.7 도달 시:**

```
AI 톤 변화: "......그 장면이 보이기 시작했어."
[1.5초 정적 — 파형만 천천히 진동]

AI: (빈 슬롯 향한 감각 심화 질문 1개)
  예: 인물은 있지만 사물이 없으면 → "그때 손에 뭘 쥐고 있었어?"
  예: 감정은 있지만 신체감각이 없으면 → "그때 몸은 어땠어?"

→ 사용자 답변 → 해당 슬롯 clarity +0.3

→ 장면 완성:
  - 모든 요소가 잠시 밝게 빛남 (0.5초)
  - 서서히 화면 한쪽으로 정리됨 (축소 + 그룹화)
  - 장면 번호 표시 없음 (사용자에게 "장면"이라는 개념 노출하지 않음)
```

**다음 장면 유도:**

```
AI: "......또 다른 순간이 있어?"

→ 사용자가 계속 말함 → 새 장면 시작 (요소 clarity 초기화, 감각 무대는 유지)
→ "없어" / 침묵(10초) / 명시적 종료 → Phase C로
```

### AI 프롬프트 설계 (Edge Function)

AI에게 매 턴 제공하는 컨텍스트:

```javascript
{
  role: 'system',
  content: `
    너는 "또다른 나". 사용자의 기억 속에서 함께 서 있는 존재.
    해석하지 마. 진단하지 마. 조언하지 마.
    반향하고, 감각을 물어봐.

    현재 장면 상태:
    - 채워진 요소: ${filledElements.map(e => `${e.type}: "${e.label}" (${e.clarity})`).join(', ')}
    - 비어있는 요소 종류: ${emptyTypes.join(', ')}
    - 장면 전환까지 필요한 요소: ${remainingCount}개

    규칙:
    - 비어있는 요소를 직접 묻지 마. 자연스러운 대화로 유도해.
    - 사용자가 행동을 나열하면, "그때 뭐가 보였어?" 같은 감각 질문으로 전환.
    - 침묵이 오면 허용해. "말하지 않아도 돼"라고 해.
    - 3개 이상 요소가 0.7 이상이면, "......그 장면이 보이기 시작했어."로 전환.
  `
}
```

## Phase C: 침전과 이별 (Sedimentation & Detachment) — 45~60초

### 진입

```
마지막 장면 완성 후, 사용자가 "없어" / 침묵 시:

AI: "......그래. 다 들었어."
[2초 정적]
입력창 서서히 사라짐 (opacity 1 → 0, 1.5초)
```

### 1단계: 정지 (5초)

```
모든 요소가 멈춤. 움직임 없음.
앰비언스(Phase A)만 유지.

Phase B에서 구성된 모든 장면의 요소가 화면에 공존:
  앵커 텍스트들, 파형들, 색조, 감정 파동.

"네가 말한 기억의 전부"가 한 화면에 보이는 유일한 순간.
```

### 2단계: 침전 시작 (15~20초)

```
요소들이 서서히 가라앉기 시작.

앵커 텍스트 → 아래로 드리프트, 자간(letter-spacing)이 벌어지며 희미해짐
파형 → 진폭 감소, 선이 가늘어짐
색조 → 채도 하강
앰비언스 → 볼륨 서서히 감소 (1.0 → 0.2)
```

**Phase A 감각 → 지층 물성 매핑:**

| Phase A 선택 | 침전 시 지층 표현 |
|-------------|-----------------|
| 냄새: rain_heavy | 짙은 청회색 지층 + 수적(물방울) 파티클 |
| 냄새: dust | 탁한 황갈색 지층 + 먼지 파티클 |
| 냄새: hospital | 차가운 백색 지층 + 직선적 경계 |
| 냄새: grass | 녹색 계열 지층 + 유기적 곡선 |
| 냄새: nothing | 무채색 지층 |
| 촉감: cold_air | 서리 파티클 효과 |
| 촉감: sweat | 습기감 (경계 블러) |
| 촉감: someones_hand | 따뜻한 갈색 계열 + 부드러운 경계선 |
| 촉감: hard_floor | 딱딱한 직선 경계 |
| 감정 색 | 지층 표면에 스며듦 (해당 감정의 RGB 블렌드) |

### 3단계: 봉인 (10초)

```
대부분의 요소가 지층 아래로 사라진 후,
화면에 입력 프롬프트 하나만 남음:

  "이 기억이 변해가도, 남아있을 한 마디."

→ 봉인어 자유 텍스트 입력

→ 봉인어가 지층 표면에 각인됨 (음각 — 파임, 돌출이 아닌)
→ 각인 순간 짧은 공명음 (앰비언스 잔향 기반)
→ 지층이 안개 아래로 사라짐 (2초)
→ 저장 완료

[전환: 메인 메뉴 또는 아카이브]
```

## 장면 수 규칙

### 범위: 최소 3개, 최대 5개

장면 수를 채우라고 유도하지 않는다. 구성요소 기반으로 자연스럽게 결정된다.

### 로직

```
장면 완성 조건: 구성요소 3개 이상 clarity >= 0.7

완성된 장면 < 3개:
  → Phase C 진입 불가. 대화 계속.
  → 사용자가 "그만할게" / 침묵(15초) 시:
     AI: "......아직 조금 흐릿해. 조금만 더 서 있어볼까."
     → 사용자가 다시 침묵(15초) 시: 
        현재까지의 요소로 장면을 강제 완성 (clarity 임계값 0.7 → 0.4로 낮춤)
        → Phase C 진입

완성된 장면 >= 3개:
  → 사용자가 "없어" / 침묵(10초) / 종료 의사 표현 시: Phase C 진입
  → 사용자가 계속 말하면: 다음 장면 시작 (5개까지)

완성된 장면 == 5개:
  → 자동으로 Phase C 진입
  → AI: "......그래. 다 들었어."
  → 유도 멘트 없음. 그냥 넘어감.
```

### 장면 수와 기억의 관계

장면이 적은 기억(3개)과 많은 기억(5개)은 질적으로 다른 기억이지, 부족한 기억이 아니다:
- 3개: 압축된 기억. 감정 궤적이 짧다. Play 모드에서 빠르게 끝남.
- 5개: 풍부한 기억. 감정 궤적이 길다. Play 모드에서 더 많은 전환 패턴 발생.
- 이 차이는 시스템이 판단하지 않는다. 기억의 밀도가 다를 뿐.

### 개념

Play가 끝날 때 플레이어는 문으로 나간다. 그 순간 **방금까지 본 장면들이 플레이어의 답변을 반영한 버전으로 다시 조립된다**. 통으로 보면 원본 기억이 아니라 **"내 답변이 녹아든 내 기억"**으로 읽힌다. 이본론("변이 = 재창조") 의 감각적 증거 지점.

### stage_1/2/3 텍스트 역할 재정의

- **버리는 프레임**: stage = 오염 단계에 따라 플레이 중 덧칠되는 텍스트
- **맞는 프레임**: stage = 문 퇴장 후 재조립에 쓰이는 **변주 텍스트 풀**. 어느 변주를 쓸지는 플레이어 궤적이 결정

### 열린 질문

- 재조립 대상: 본 장면 전부 vs 핵심 장면만
- 표시 형식: 원본과 나란히 비교 vs 변주만 단독
- 답변 → 변주 선택 규칙 (감정 궤적 / 선택지 감정 누적 / 오염 bucket 중 무엇?)
- 재조립 결과가 archive에 별도 저장되는가, 개인 경험으로만 소비되는가

### 데모 scope (2026-04-18 결정)

fixation 복합신호, 재조합 트리거, 문→장면화 — **3개 다 데모 영상에서 제외**. v2로 연기.

# 잔상(殘像) 시스템 설계

> 작성: 2026-04-09
> 해결 대상: Feedback #4 (남의 기억 위화감), #8/#11 (맥락 부재)
> 상태: 설계 초안 / 구현 전
> 영문 명칭: **Afterimage**

---

## 1. 배경 — 왜 잔상인가

### 1.1 풀고자 하는 문제

- **#4** 관객이 "남의 기억을 내 것처럼 말하는" 위화감을 호소했다. 지금까지 이것을 버그로 보고 프롬프트로 막으려 했다.
- **#8, #11** 장면이 끝난 직후, 관객에게 남는 것이 없다. 봉인/전이가 일어나도 피드백이 없다.

### 1.2 입장 전환

위화감을 **버그가 아니라 작품의 테제**로 승격시킨다.

> 기억은 원래 남이 했던 말을 내 것으로 착각하는 것이다.
> — **Cryptomnesia (잠재기억)**, 임상심리학 현상

지금 작품은 "텍스트 글리치, 감정 벡터 드리프트" 같은 *기계적* 은유로 오염을 표현한다. 잔상 시스템은 이 은유를 **사회적 층위**로 확장한다: 관객의 기억 풍경은 **타인의 파편**으로 오염된다.

### 1.3 심심이 비유

LLM 생성이 아니라 **DB 조회 기반**의 옛 챗봇 구조를 차용한다.
- 반-LLM 포지셔닝 (2026년 AI 과열기 맥락에서 전략적)
- 레이턴시 0, 비용 0
- 관객이 읽는 모든 문장은 **진짜로 누군가가 한 말**

---

## 2. 설계 원칙

1. **먼저 말하지 않는다.** 잔상은 장면이 끝난 직후, 정적이 흐르는 순간에만 등장한다.
2. **드물어야 한다.** 모든 플레이에서 뜨지 않는다. 등장 자체가 사건이 되어야 한다.
3. **절대 확신할 수 없다.** 일부는 진짜 관객의 말이고, 일부는 타인의 말이다. 비율은 공개하지 않는다.
4. **한 번에 하나만.** 여러 잔상이 동시에 뜨면 카오스가 된다.
5. **설명하지 않는다.** "This was yours" 같은 대사는 초반 1-2회만. 이후 관객이 스스로 의심하게 둔다.
6. **허락받은 말만 쓴다.** 관객이 명시적으로 공개에 동의한 utterance만 풀에 들어간다.

## 4. 수집 파이프라인

### 4.1 Record 세션 종료 시

1. `collect-memory` Edge Function이 기억 추출 완료 후, 후보 발화 3-5개를 `utterances`에 `is_public=false`, `source_type='record'`로 저장.
2. 관객에게 **마지막 동의 화면** 표시:

   > 이 기억의 조각이, 누군가 다른 이의 장면 끝에 떠오를 수도 있어요. 허락할까요?
   > [ ] 전부 허락  [ ] 고르고 싶어요  [ ] 남기지 않을래요

3. 허락한 항목만 `is_public=true`로 승격. 나머지는 보관 또는 삭제 (설정에 따라).

### 4.2 Play 중 관객 입력 (scene_input)

Play 중 관객이 직접 타이핑한 응답도 후보다. 단:
- 기본은 `is_public=false`.
- Play 종료 화면에서 일괄 동의 요청.

### 4.3 시드 코퍼스

콜드 스타트 방지용. **작가(너) 본인과 초기 테스터 5-10명**의 발화 50-100개를 수동으로 큐레이션해 `source_type='seed'`, `is_public=true`, `moderation_status='approved'`로 선주입.

전시 문구에 이렇게 쓰면 작품이 된다:

> 이 작품은 처음엔 작가의 말로 시작해, 관객의 말로 번져갑니다.

---

## 5. 모더레이션

### 5.1 자동 필터 (저장 시점)

저장 전 Edge Function에서 검사:
- 개인 식별 정보 (이름/전화/주소) 탐지 → 자동 rejected
- 혐오/자해/폭력 키워드 → 자동 pending + 플래그
- 너무 짧거나(3자 미만) 너무 긴(280자 초과) → 자동 rejected
- 영어-한국어 언어 감지 → `lang` 세팅

### 5.2 수동 검토 (관리자)

`moderation_status = 'pending'` 항목만 `admin.html`에서 검토 → approved 또는 rejected.

### 5.3 사후 철회

관객이 프로필에서 자기 utterance를 언제든 `is_public=false`로 돌릴 수 있어야 한다. (GDPR 유사 권리)

---

## 6. 매칭 전략

### 6.1 v1 (MVP) — 룰 기반 스코어링

방금 끝난 장면의 컨텍스트로 후보를 고른다.

입력: `{lang, emotion_tags, keywords, axis_x, axis_z}`

쿼리:
```sql
SELECT id, text, score
FROM utterances
WHERE is_public = true
  AND moderation_status = 'approved'
  AND lang = $1
  AND id NOT IN (이 viewer가 이미 본 utterance)
ORDER BY (
  -- 키워드 겹침 가중치
  cardinality(keywords & $keywords) * 3 +
  -- 감정 태그 겹침
  cardinality(emotion_tags & $emotion_tags) * 2 +
  -- 축 거리의 역수 (가까울수록 높음)
  (2 - abs(axis_x - $axis_x) - abs(axis_z - $axis_z)) * 1
) DESC,
  random() * 0.3  -- 일부 무작위성
LIMIT 5;
```

그 중 **top 5에서 랜덤 1개**를 고른다. 완벽한 1등만 고르면 알고리즘처럼 느껴진다.

### 6.2 비율 조절 — 진실 30% / 타인 70%

- 30% 확률: **이 관객 본인**의 과거 발화 (있으면)
- 70% 확률: 타인의 발화

둘 다 같은 연출로 뜨고, 같은 메시지("…네가 한 말이야")로 설명된다. 관객은 진위를 알 수 없다. 그게 요점이다.

본인 발화가 없는 신규 관객은 100% 타인. 첫 플레이가 가장 거짓에 가깝고, 회차가 쌓일수록 진실이 섞인다. **작품이 관객을 알아갈수록 관객의 정체성이 흐려진다** — 역설이 의도된 것이다.

### 6.3 등장 빈도

- 씬 종료 시 50% 확률. 매번 뜨지 않는다.
- 한 플레이 세션 내 최대 2회.
- 같은 utterance는 같은 viewer에게 두 번 뜨지 않는다.

### 6.4 v2 — pgvector 임베딩

seed 100개 돌파 후:
- `collect-memory`에서 저장 시 `text-embedding` 모델로 384차원 벡터 생성
- `<=>` 코사인 거리로 가장 가까운 발화 매칭
- 룰 기반과 임베딩 기반을 8:2로 블렌드

---

## 7. 연출 명세

### 7.1 트리거

장면이 "닫힘" (fadeout 완료 후) + 0.8초 정적.

### 7.2 등장

- 화면 중앙에서 약간 아래, **시야 주변부**에 서서히 떠오른다.

# 데이터 계약 v1 — Bridge / Emotion Entry / Trajectory Bridge

작성일: 2026-04-12
상태: 확정 (MVP)
관련: 시각화_설계_v1-260412.md

---

## 결정 요약

비선형 소설을 TEM에 얹기 위한 신규 데이터 구조 합의. 기존 Scene/Choice 스키마는 손대지 않고 **확장**한다.

---

## 1. 새 개념 정의

### Author Bridge (작가 브릿지)
- 작가가 직접 쓴 해석 단서 조각.
- 씬 본문은 건드리지 않고 **씬 주변에 부가 표시**.
- 플레이어가 선택적으로 펼쳐서 봄. 필수 아님.
- 불변 (또는 작가가 명시적으로 수정).

### Trajectory Bridge (궤적 브릿지)
- **공명 엔딩에 도달한 플레이어의 궤적이 자동으로 변환된 브릿지**.
- 별도 승인 절차 없음 (공명 도달이 곧 승인).
- 다음 플레이어가 **비슷한 궤적**을 걸을 때 노출.
- 비슷한 궤적 = 같은 감정 진입점 + 핵심 통과 씬 1~2개 일치.

### Emotion Entry (감정 진입점)
- 작품 단위로 정의되는 **감정 → 시작 씬 매핑**.
- 1 감정 : 1 시작 씬 (1:1 고정).
- 키는 영어 (기존 `original_emotion` 키와 일관: sadness, longing, fear, guilt, anger, shame, numbness, isolation).

---

## 2. 스키마

### Scene 확장 필드
```js
{
  // ... 기존 필드 ...
  motif_tags: ["chasai", "footsteps"],   // 이 씬의 공명 모티프 (영어 권장)
  author_bridges: [
    {
      id: "ab-letter-E-1",
      text: "짜사이는 원래 중국집에서만 먹던 것.",
      reveal_hint: "엄마의 식탁을 다시 본다"   // optional
    }
  ]
}
```

### Work (작품) 확장 필드
```js
{
  // ... 기존 필드 ...
  emotion_entries: {
    longing:  "s-letter-A",
    fear:     "s-letter-D",
    guilt:    "s-letter-H",
    sadness:  "s-letter-E",
    anger:    "s-letter-F",
    numbness: "s-letter-J"
  }
}
```

### Trajectory Bridge (별도 테이블)
```js
{
  id: "tb-...",
  work_id: "E-004",
  scene_id: "s-letter-E",                // 어느 씬 주변에 노출되는가
  source_run_id: "...",                  // 어떤 플레이가 만들었나
  source_completed_sentence: "...",      // 그 플레이의 최종 문장 (브릿지 본문 후보)
  trajectory_signature: {
    entry_emotion: "fear",
    key_passed_scenes: ["s-letter-D", "s-letter-E"]
  },
  created_at,
  status: "live" | "hidden"              // hidden은 신고/관리자 차단 시
}
```

---

## 3. 매칭 규칙

다음 플레이어가 trajectory bridge를 보려면:
- `trajectory_signature.entry_emotion` 일치
- `trajectory_signature.key_passed_scenes` 의 **전체 또는 부분 일치 (≥1개)**

key_passed_scenes 추출 기준은 작가가 작품마다 지정 (작품 객체에 `key_scenes: [...]` 필드 추가).

---

## 4. 명시적 비도입 (Phase 1)

다음은 **하지 않는다**:
- 공명 점수 / 좋아요 / fade / hide 자동화
- 브릿지 발동의 연쇄 반응
- 런타임 ContaminationTracker와 브릿지 발동의 연동
- 익명/실명 표시 (브릿지 본문에 작성자 정보 일체 표시 안 함)
- 페이스북식 인게이지먼트 메커닉

---

## 5. 보류 항목 (별도 결정 필요)

- **공명 궤적이 브릿지가 될 때 다음 플레이어에게 노출되는 연출**: completed_sentence 그대로? 경로 모양만? echo_words 잔상? → 추후 결정.

# 다궤적 시각화 UI 설계 v1

작성일: 2026-04-12
상태: 확정 (MVP)
관련: 데이터계약_브릿지_v1-260412.md

---

## 설계 프레임: 3뷰 분리

세 가지 다른 질문은 한 시각 문법으로 못 답한다. 뷰를 나눈다.

| 뷰 | 답하는 질문 |
|---|---|
| 전역 흐름 뷰 | "어디서 갈라지고 어디서 모이는가" |
| 국소 그래프 | "이 씬 주변에 뭐가 걸려 있는가" |
| 의미 비교 패널 | "같은 씬이 경로별로 어떻게 달라지는가" |

---

## 1. 전역 흐름 뷰

- **레이아웃**: DAG. dagre로 좌표 계산. force-directed 금지 (mental map 안정성).
- **x축**: 서사 진행 (위상 깊이 또는 작가 지정 단계).
- **y축**: 교차 최소화 자동 정렬.
- **기본 상태**: 빈 캔버스. 좌측 감정 체크박스(8개)에서 1~3개 선택해야 그려짐.
- **전체 토글**: 둠. 기본 off.
- **노드 표시**: 씬 ID/제목 + 통과 궤적 수 카운터(뱃지) + 브릿지 존재 뱃지.
- **노드 시각 변수**(크기/glow): MVP에서 미사용. 텍스트 정보로 대체.

### 브릿지 처리 (전역 뷰)

- **DAG 토폴로지에서 제외**. dagre 입력은 choice edge만. 브릿지는 좌표 계산 후 오버레이로 그림.
- **두 종류 시각 구분 필수** (Phase 1부터 UI 자리 잡아둘 것):
  - Author bridge 뱃지: 회색 `[🔗 motif]`
  - Trajectory bridge 뱃지: 푸른빛 `[🌊 entry_emotion]`
- 기본 상태에서는 뱃지만. 감정 궤적 선택 시 해당 궤적에서 발동하는 브릿지만 edge로 표시 (choice edge와 색/dash 패턴 구분).
- **"모든 브릿지 보기" 토글**: 둠. 기본 off. 편집 초기 단계용.

---

## 2. 의미 비교 패널

- **트리거**: 전역 뷰 노드 클릭 시 우측 패널.
- **은유**: Git diff. 그래프가 아니라 텍스트 비교 도구.
- **내용**: 해당 씬에 도달하는 궤적을 행으로 나열. 각 행에:

## 1. 파동(Wave) 계열 — 4종

### 1.1 라이브 감정 파동 (Live Emotion Wave)
- 정의: 사용자 실시간 감정 분석 결과 시각화
- 계산: `computeWaveFromEmotion()` — amplitude = intensity, frequency = 0.01 + complexity*0.005
- 위치: `js/index.js`, `js/app/live.js`, `js/app/recordChat.js`
- 용도: 라이브 세션, 고백 모드, 비교 뷰

### 1.2 아카이브 파동 (Archive Wave)
- 정의: 회상 중 감정 궤적을 사후 저장하는 파형
- 계산: `computeArchiveWaveData()` — wave point 배열 생성, width는 텍스트 길이 의존
- 저장: `plays.wave_data`
- 비교 뷰에서 **사용자 파동만** 표시 (원본 숨김)

### 1.3 Admin 파동 (Admin Preview Wave)
- 정의: 관리자 대시보드 기억 감정 미리보기
- 계산: `computeWaveData()` (admin.js) — 감정별 파동 **합산** (아카이브/라이브와 다름)
- 플레이에 영향 없음, 시각화 전용

### 1.4 Strata 파동 (Strata 3D Wave)
- 정의: 3D 지형 표면의 물결/색상 맥동
- 파형 아님 (지형 움직임)
- 파일: `js/ui/strataView.js`, `js/shared/tem_af_strata_terrain.js`
- cont_stage와 연동

## 2. 잔상(Afterimage) 계열

### 2.1 관객 발화 잔상 (Utterances Afterimage)
- 이전 관객 짧은 발화(≤280자)를 다음 관객이 "자신 말처럼" 목격
- 테이블: `utterances`, `afterimage_events`
- 매칭: 키워드×3 + 감정태그×2 + 축거리×1, 상위5 중 랜덤1

- 씬 종료 후 50% 확률, 플레이당 최대 2회
- 파일: `js/lib/afterimage.js`, Edge Function `match-afterimage` (예정)
- 문서: `docs/잔상_시스템_설계-260409.md`

### 2.2 부유 앵커 (Floating Anchor)

- 파일: `js/ui/floatingAnchor.js`

### 2.3 Echo Words
- 작가가 장면에 사전 설정한 키워드 배열

## 6. 좌표계 — 2종

### 6.1 VAD (3차원 감정)
- Valence: 부정↔긍정
- Arousal: 저진정↔고진정
- Dominance: 무력↔우월
- 용도: 수학/시각화 기본 (지도 핀, 지형 투영)

### 6.2 AF 좌표 (2차원 해석)
- Attribution: 자기탓↔남의탓/운명
- Core Fear: 핵심 두려움 축
- V3에서 폐기, V4는 궤적으로 대체
- 현재: Strata 3D 투영, 오염 방향

## 7. 오염 계열 — 3가지 차원

### 7.1 2축 MVP — Drift & Fixation
- **cont_drift**: 원본에서 틀어진 정도 (0~1), EMA α=0.10
- **cont_fixation**: 특정 해석으로 굳어진 정도 (0~1)
- Stage 판정:
  - drift > fixation → Stage 1 "biased_inclination"
  - fixation > drift → Stage 3 "hypercompletion"
  - 평형 → Stage 0 "stable"
- 파일: `js/core/ContaminationTracker.js`
- 문서: `docs/Contamination_MVP_Spec_v3-260327.md`

### 7.2 3축 V2 — Divergence / Convergence / Heterogeneity
- **cont_divergence**: 원본 누적 거리 (분자시계 포화)
- **cont_convergence**: 반복 고정렬 과잉 수렴 (depth≥3부터)
- **cont_heterogeneity**: 해석 간 정렬도 분산 (Welford)
- Stage 혼합:
  - stage_1 = divergence × (1-convergence)
  - stage_2 = heterogeneity × min(depth/5, 1)
  - stage_3 = convergence × (1-heterogeneity)
- 문서: `docs/오염벡터_계산_구현_명세_v2-260327.md`

### 7.3 Stage 라벨 (연출용)
- Stage 0: stable
- Stage 1: biased_inclination (편향적 기울어짐, 수정 가능)
- Stage 3: hypercompletion (과잉 완결, 병리적)

## 8. 정렬도 계열

### 8.1 Alignment (V4 공식)
```
alignment = level × shape × void_mod
```

- **level**: scene_score(감정 코사인) 평균
- **shape**: 감정 변화 방향 유사도 (TIES 이론), 장면≥3일 때만
- **void_mod**: VOID 페널티 (플레이어 VOID & 기록자 입력 → ×0.7)

### 8.2 Bucket
- ≥0.55 HIGH / 0.35~0.55 MID / <0.35 LOW
- 마지막 3회 감정 동일 → FIXATED (우선)

### 8.3 변천
- V3: 감정(0.4) + 이유(0.4) + 태도(0.2)
- V4: 이유는 궤적으로 암시 → level × shape × void_mod

## 가시적 Flow (프레임 순서)

### Frame A — 인트로 + 입력

- 검은 배경
- 가운데 한 가닥 실(wavy line, SVG sine wave) — 한 세그먼트가 간헐적으로 깜박
- 대사 1 타이핑 효과로 등장 (0.8~1.2s)
- 대사 2, 3 순차 페이드인 (각 1.5s 간격)
- 맨 아래 텍스트 입력 필드 페이드인 (placeholder 없음, 포커스 자동)
- 엔터 또는 보내기 버튼으로 제출
- 입력 필드 아래 작은 링크: "아카이브 직접 둘러보기 →" / "browse archive" (자유 탐색 back door)

### Frame B — 분석 중

- 실이 답변을 흡수하듯 진동 (1~3s)
- 백엔드: claude-scene `play_entry_match` 호출 중

### Frame C — 180° 회전 + 3 문

- 화면 컨테이너 Y축 180° 회전 (CSS `transform: rotateY(180deg)`, 1.2s)
- 뒷면에 3 문이 ASCII 스타일로 정적 렌더 (confession.js `doorPhase 0` 활용)
- 문 3개 수평 병치, 간격 균등

### Frame D — 호버 / 선택

- 문 호버 → 해당 메모리의 혼잣말(DB pool에서 고른 한 줄) 문 위쪽에 페이드인
- 오염된 메모리:
  - `biased_inclination` → 가운데점(`·`) 몇 개 박힘
  - `hypercompletion` → `░▒▓` 과선명 텍스처 섞임
- 문 클릭 → 해당 문이 열리는 애니메이션 (doorPhase 1 → 2, 약 2s)
- 열린 문을 통과하는 모션

### Frame E — 브릿지 한 줄

- play 시작 직전: "이 기억이 반응했다." (한 줄, ko) / "this memory responded." (en)
- 1초 후 fade → 첫 씬 시작

## 백엔드 — claude-scene 확장

**새 type 추가:** `play_entry_match`

```
Request:
{
  type: 'play_entry_match',
  userText: string,
  locale: 'ko' | 'en',
  memories: [{
    id: string,
    completed_sentence: string,
    echo_words: string[],
    original_emotion: { [emotion]: number },
    cont_stage?: 'biased_inclination' | 'hypercompletion' | null,
    sample_scene_texts: string[]  // 상위 2~3 씬 텍스트 (혼잣말 pool)
  }]
}

Response:
{
  baselineEmotion: { fear: 0.3, guilt: 0.2, ... },   // 8차원
  picks: [
    {
      memoryId: string,
      monologue: string,          // DB에서 꺼낸 또는 재배열한 문장 1줄
      variance: 'resonance' | 'variation' | 'drift',
      contamination: 'clean' | 'biased_inclination' | 'hypercompletion'
    },
    ...
  ]
}
```

**LLM 프롬프트 지침 (v1 6-4 원칙 계승):**

1. userText에서 8차원 감정 벡터 추출 (기존 emotion_analysis 루틴 재활용 가능)
2. 메모리마다 cosine 유사도 계산
3. 3개 선택:
   - 1st (`resonance`): 유사도 top-1
   - 2nd (`variation`): top 3~5 중 뚜렷한 결 차이
   - 3rd (`drift`): top 10 내 의외성. 추천엔진 방지용
4. 각 pick에 대해 **해당 메모리의 completed_sentence / echo_words / sample_scene_texts 풀에서만** 혼잣말 1줄 고름
5. **새 문장 생성 금지**. 재배열·발췌만 허용
6. cont_stage 있으면 contamination 필드에 그대로 태깅 (실제 오염 텍스처는 프론트가 렌더)

# 별이엔진 단일화 — 갈아끼우기 전 베이스라인 대조 (2026-05-18)

## 목적

play-test.html은 별이엔진 로직을 인라인 함수 `byeoriCalculateStep`(2082줄)으로 **복사해서** 갖고 있다.
이를 진짜 모듈 `js/core/ByeoriEngine.js`의 `calculateStep`으로 단일화한다(통합 후보 1).
코드를 건드리기 전에, 두 구현이 실제로 어디서 어떻게 다른지 한 줄씩 대조한 기록.

## 대조 대상

- 모듈 원본: `js/core/ByeoriEngine.js` — `calculateStep` / `_getMismatchType` / `_getTransitionPattern`
- play-test 복사본: `play-test.html` — `byeoriCalculateStep`(2082) / `getMismatchType`(2048) / `getTransitionPattern`(2065)

## 대조 결과

| 조각 | 차이 | 행동 영향 |
|---|---|---|
| getMismatchType | 없음 — 완전 동일 | 없음 |
| getTransitionPattern | 인자 1개 차이(origTraj). displacement 조기판정에서 원본은 `userTraj.length>=3 && origTraj.length>=3`, 복사본은 `userTraj.length>=3` | **없음** — userTraj/origTraj는 매 호출 짝으로 push되어 길이가 항상 같음 → 두 조건은 동치 |
| byeoriCalculateStep 본체 (level / shape / void / alignment / bucket / mismatch / transition_pattern) | 없음 — 식·함수 동일 | 없음 |
| affective_position | 원본 `projectEmotionToVAD(base, anchorEmotions)`, 복사본 `projectEmotionToVADContour(base)` — **다른 함수** | **있음** — 좌표 산출 방식이 다름 |

## 결론

**유일한 행동 차이는 `affective_position` 한 필드뿐이다.** alignment·bucket·transition_pattern·mismatch_type
은 두 구현이 동일하게 산출한다.

> 주의: 앞선 세션 대화에서 "transition_pattern displacement 판정이 갈아끼우면 달라진다"고 했으나,
> 정밀 대조 결과 **달라지지 않는다.** origTraj 길이 조건은 userTraj 길이 조건과 항상 동치인 중복 조건이었다.

`affective_position`은 LUMEN 3D 등고선 지형에서 핀·앵커 위치 계산에 쓰이며, play-test는 등고선
전용 변형판 `projectEmotionToVADContour`를 의도적으로 쓴다. 엔진 내부 계산에는 `affective_position`
이 전혀 쓰이지 않으므로(반환 객체에만 담김), 갈아끼운 뒤 이 필드만 덮어쓰면 된다.

## 갈아끼우기 계획 (다음 단계)

play-test.html 모듈 블록(`<script type="module">`, 508줄~)에 import 한 줄을 더하고, 인라인 본체를
얇은 wrapper로 교체한다:

```js
import { calculateStep } from './js/core/ByeoriEngine.js';   // 추가

function byeoriCalculateStep(input, context) {
  const r = calculateStep(input, context);
  r.affective_position = projectEmotionToVADContour(
    (input.userVector && input.userVector.base) || input.userVector
  );
  return r;
}
```

- 인라인 본체(2082~2129) → 위 wrapper로 교체.
- `getMismatchType`(2048)·`getTransitionPattern`(2065): byeoriCalculateStep 외 사용처가 없으면
  제거(착수 시 grep으로 확인). `projectEmotionToVADContour`는 3787줄에서도 쓰므로 유지.
- 호출 4곳(3623 / 3649 / 3689 / 3713): 함수 이름이 그대로라 무수정.

이 wrapper를 쓰면 play-test의 **관측 가능한 행동은 현재와 완전히 동일**하다. 변하는 것은
"엔진 로직이 검증된 단일 출처에서 온다"는 사실뿐 — 복사본 갈라짐(drift) 위험이 사라진다.
